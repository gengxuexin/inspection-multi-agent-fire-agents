# 评测可信度机制

> 为什么需要这一套：**RAGAS 的分数会骗人。**

---

## 一、一次真实的翻车

2026-10-15 那天，我在调 RAG 检索参数，连续跑了三轮评测：

| 轮次 | faithfulness | answer_relevancy | context_precision | context_recall |
|------|-------------|-----------------|------------------|----------------|
| v7 | 0.985 | 0.706 | 0.221 | 0.548 |
| v8 | 0.993 | 0.694 | 0.226 | 0.569 |
| v9 | — | — | — | — |

看起来 `rel +0.127`、`prec +0.004`、`recall +0.021` —— 有涨有跌，像是"调优在起作用"。

**我把其中一部分写进了结论文档，当成有效证据。**

后来逐条比对 `contexts` 才发现：**三轮的检索结果逐字完全相同。**

```
v7 contexts 指纹 = cb941a0116de7cef
v8 contexts 指纹 = cb941a0116de7cef   ← 一样
v9 contexts 指纹 = cb941a0116de7cef   ← 还是一样
```

是**空跑**。检索层压根没变，分数的差异 100% 来自 LLM 判分自身的随机性。

---

## 二、为什么会踩这个坑

三个条件同时具备，缺一不可：

1. **检索层真的没变** —— 比如改了精排代码但索引没重建、或者改动写错了地方
2. **分数确实变了** —— 因为 LLM judge 有随机性，同样的输入两次打分不同
3. **没有对照基线** —— 没有"上一轮的 contexts 指纹"可比对

第 2 点是根源。实测抖动约 **0.021**，而我当时观察到的变化是 0.004 ~ 0.021 —— **全在抖动量级以内**。

> 一个认知偏差：**人看到数字变化就倾向于解读为"有原因"**，
> 尤其当你刚花了几个小时调参、心里预期它有效时。
>
> 这不是判断力问题，是需要机制来对抗。

## 三、三项机制

### 1. 上下文指纹（变量隔离）

```python
def contexts_fingerprint(details: list) -> str:
    h = hashlib.sha256()
    for d in details:
        h.update((d.get("question") or "").encode("utf-8"))
        for c in (d.get("contexts") or []):
            h.update(c.encode("utf-8"))
        h.update(b"\x00")
    return h.hexdigest()[:16]
```

**指纹绝不能包含答案和分数。**

这一点是整个机制成立的前提：如果指纹含分数，那么分数一变指纹就变，
空跑检测立刻失效 —— 而空跑检测恰恰是三项里最有用的一项。

> 反向验证（`deploy/tools/test_baseline_diff.py` 有这项）：
> 把一份报告的四个指标全改成 0.99，指纹仍然是 `cb941a0116de7cef`。
> 改一条 `contexts`，指纹立刻变成 `2c294669af043ded`。

### 2. 空跑检测

指纹一致 → 检索层零变化 → **无论分数怎么变都不能作为结论**。

`compare_with_baseline()` 在这种情况下返回退出码 1，
`local_eval.py` 直接 `sys.exit(1)` —— **不是打个警告，是阻断**。

理由：错误的结论一旦被写进文档，就会被当成面试素材带出去。
与其让人事后发现，不如当场拦住。

### 3. 噪声底

```python
_NOISE_FLOOR = 0.05      # 实测抖动约 0.021，取 2.4 倍余量
```

**为什么不是 0.021：**

最初就是用实测值 0.021 设的阈值。结果 v7→v8 的 recall 差值恰好就是 0.021，
`abs(0.021) > 0.02` 判真，测试直接失败。

> 教训：**单次 A/B 差值只是抖动幅度的下界，不是幅度本身。**
>
> 你只观察到了那一次波动，不能据此断定抖动不会更大。
> 阈值取实测值，等于把判定建在最脆弱的边界上。

## 四、怎么用

```bash
# 第 1 轮：正常跑
python agent1/eval/local_eval.py \
    --samples agent1/eval/qa_samples.jsonl \
    --top-k 5 --output report_v10.json

# 第 2 轮：与上一轮对比（自动做空跑检测 + 噪声判定）
python agent1/eval/local_eval.py \
    --samples agent1/eval/qa_samples.jsonl \
    --top-k 5 --output report_v11.json \
    --baseline report_v10.json
```

输出示例：

```
  上下文指纹  本轮=a1b2c3d4e5f6a7b8  基线=9f8e7d6c5b4a3f2e
    -> 检索层已变化

  指标                       基线       本轮        差值
  ----------------------------------------------------
  faithfulness             0.9850   0.9930   +0.0080
  answer_relevancy         0.7060   0.6940   -0.0120
  context_precision        0.2210   0.2260   +0.0050
  context_recall           0.5480   0.5690   +0.0210

  [可作结论] 超出噪声底（±0.05）：
       （无）
  [不可作结论] 未超出噪声底：
       faithfulness         +0.0080
       ...
```

**输出会明确区分「可作结论」和「不可作结论」**，
而不是让人自己看数字猜。

## 五、A/B 对照的正确做法

只跑一轮新代码、和历史报告比，**是不行的** ——
历史报告里往往混着别的改动，变量不隔离。

正确流程（`deploy/tools/ab_rerank.sh` 已自动化）：

1. 同一份索引、同一批样本、同一模型
2. **只切一个变量**（本例是精排），跑两轮
3. 对比时带 contexts 指纹

```bash
bash deploy/tools/ab_rerank.sh
```

脚本会在跑完后**务必把代码切回新版本** ——
否则下次跑评测用的是旧逻辑，而这一点不会有任何提示。

## 六、还缺的机制

诚实列出来：

1. **样本量偏小**：46 条，单指标差值的标准误在 0.03 量级，
   比噪声底还大。现在的机制能检出空跑，但**检出不了小效应**。
   要检出 0.02 量级的真实提升，需要 200+ 条或多次重复取平均。

2. **LLM judge 随机性没有真正消除**：
   根治办法是同一份 contexts 打分 3 次取平均（成本 3 倍），
   或者用更强的 judge 模型。都没做。

3. **没有分层统计**：47 条里 `category`（直查法条/跨文档综合/陷阱题）
   与 `difficulty`（easy/medium/hard）分布不均时，总分会掩盖子集的退化。
   应该按分层分别看。

4. **弃答样本未单独统计**：合理弃答（检索不到就该拒答）与过度保守
   （有答案却拒答）在总分里表现一样，但业务后果完全不同。
   现有 `assess` 逻辑能区分，但没进报告的正式指标。

## 七、面试时怎么讲这个

**别讲"RAGAS 分数提升了多少"，讲你怎么保证那个数字可信。**

可以这么说：

> 我调 RAG 的时候踩过一个坑：连跑三轮，分数有涨有跌，
> 以为是调优见效。后来逐条比对发现三轮的检索结果完全一样——
> 是空跑，差异全来自 LLM 打分的随机性，实测抖动 0.021。
>
> 所以我加了三道机制：上下文指纹（只哈希检索结果，不含答案和分数）、
> 空跑检测（指纹一致就阻断，不让结论写出去）、噪声底（0.05，
> 而不是实测的 0.021，因为单次差值只是抖动幅度的下界）。
>
> 后来每次对比检索策略，都带指纹比对。**有时候结论是"这轮没效果"——
> 这也是结论。**

这段话的价值在于它展示的是：
- 知道自己的测量方法会骗人
- 用机制而不是判断力来对抗
- 愿意接受"没效果"这个结论

最后一条尤其重要 —— 大多数人会不自觉地只保留支持自己判断的数据。
