# 消防智能执法多模态 Agent 系统 —— 项目说明书

> 面向面试展示的技术文档。重点不是"用了什么框架"，而是**问题怎么被发现、方案怎么被验证、结论怎么被确认**。

---

## 一句话定位

一个把 **103 份消防法规文档、4019 个语义分块**变成可追溯问答能力的 RAG 系统，  
外加多模态案件分析与法律文书自动生成的编排层。

**最值得讲的部分**：我不是"接了个向量库做问答"，而是用**可量化的评测驱动**定位瓶颈、  
逐层定位根因、每一步都验证过的优化过程。详见 [RAG 调优路径](./rag-tuning-journey.md)。

## 二、系统架构

```
                        ┌─────────────────────────┐
   客户端 ──JWT/OIDC──▶ │  Gateway (440行)        │
                        │  鉴权 · 审计 · 限流      │
                        └───────────┬─────────────┘
                                    │
                    ┌───────────────▼───────────────┐
                    │   LangGraph 状态图编排        │
                    │  classify → (vision|voice|    │
                    │   doc_extract) → synthesize   │
                    │  → extract_fields → generate  │
                    │  条件边 + 最大跳数 + 转人工    │
                    └───────┬───────────┬───────────┘
                            │           │
              ┌─────────────▼──┐   ┌────▼─────────┐
              │ Agent1         │   │ Agent2 / 3    │
              │ RAG + 文书生成 │   │ 语音 / 视觉    │
              └───────┬────────┘   └────┬─────────┘
                      │                   │
              ┌───────▼───────────────────▼───────┐
              │  三态熔断 · 预算闸门 · 全链路追踪   │
              │  （common/resilience.py 等）        │
              └───────────────────────────────────┘
```

### 关键设计取舍

**1. 三级级联路由（L1 → L2 → L3）**

不是"一个大模型处理所有输入"，而是先用轻量分类器路由，只在置信度不足时  
才升级到 LLM 判断。`ROUTE_MAX_HOPS=3` 兜底，超限直接转人工 —— **AI 系统的  
失败路径必须显式设计**，不能让它无限重试。

**2. 三态熔断而非二态**

`CLOSED / OPEN / HALF_OPEN`。半开态的存在是为了避免"服务刚好恢复就被  
一波流量打死"这种典型雪崩。

**3. LLM 主备链（2026-10-15 新增）**

DeepSeek 挂掉导致整个链路停摆后，我把它改成：主 DeepSeek，失败自动切  
阿里云通义千问，**13 个业务文件零改动**、调用方无感知。

关键设计是**故障必须可观测**：切换时明确打日志、评测报告记录当轮用的  
provider 链、统计因故障未生成答案的条数并警告"本轮不可与其他轮对比"。

> 功能对了但日志说不清发生了什么，等于没做。

## 三、我在这个项目里真正做了什么

这一节是重点。以下每一条都是**实际问题 → 定位过程 → 方案 → 验证**的完整闭环。

### 3.1 RAG 检索质量：从"感觉不好"到"可量化归因"

**问题**：初版 RAGAS 四项指标里 `context_precision` 只有 0.165。

**难点**：这不是检索算法不够好，而是**不知道差在哪**。总分掩盖了结构性问题。

**做法**：

1. **扩充评测集**：5 条 → 47 条，人工标注，覆盖 3 类场景（直查法条 /  
   跨文档综合 / 陷阱题）× 3 档难度。原始 7 条完整保留，保证与早期结果可比。
2. **分层统计**：按 category / difficulty 分组算指标，避免"直查法条 0.95  
   但跨文档 0.4"这种关键差异被总分掩盖。
3. **同口径归因**：老 7 条与新增 40 条分开统计，避免把"新样本拉低总分"  
   误判成"代码退化"。

**发现**：陷阱题 recall 恒为 0，且 4/6 都与《消防产品目录》有关。

→ 完整 5 轮调优过程见 [RAG 调优路径](./rag-tuning-journey.md)。

**结果**（47 条 / top_k=5）：

| 指标                | 初始    | 现在        | 备注                        |
| ----------------- | ----- | --------- | ------------------------- |
| faithfulness      | 0.986 | 0.985     | 始终保持高位                    |
| answer_relevancy  | 0.579 | **0.706** | +0.127，且 faithfulness 零代价 |
| context_recall    | 0.527 | **0.548** | 陷阱题 0.167 → 0.333（翻倍）     |
| context_precision | 0.165 | **0.221** | +34%                      |

**一个值得单独讲的结论**：

> "多作答不换来幻觉。"  
> 我降低了 23 条弃答（模型从"检索内容不足"改为基于现有片段作答），  
> faithfulness 一条没掉（0.985 → 0.985）。这推翻了我原本"答得多会编"的假设，  
> 而**推翻假设的过程本身就是产出**。

### 3.2 PDF 视觉结构丢失：分块层的根因治理

**问题**：检索不到某个产品条目，逐层排查发现——**答案其实完整存在于一个  
306 字的 chunk 里，BM25 明确把它排在第 1 名**，但被挤出 top-k。

**根因**：PDF 的视觉结构在转纯文本后消失。"一、电线电缆（3 种）"和  
"1.不包括阻燃电线电缆…"是两行独立内容，入库时被切在一个大 chunk 里，  
和自我声明说明粘在一起，bag-of-words 无法对齐。

**方案**：在**入库前**恢复结构，让"一个条目 = 一个语义单元"。

这里踩了三个坑，都写进了注释：

| 坑                | 错误做法    | 为什么失败                                                                      |
| ---------------- | ------- | -------------------------------------------------------------------------- |
| 判据用"中位间隔 ≤ 12 行" | 看起来合理   | 真实文档每个大类下是一整张几十行的产品表，35 个切点的中位间隔是 **95 行**，任何"间隔要小"的阈值都会误判                 |
| 标准号只要求"行首匹配"     | 能命中目标文档 | 导则正文里 `GB 50354 等技术标准…` 是**句内引用**，行首一匹配就把 8,561 行正文切碎                      |
| 优先级排在档位表之后       | 顺序无所谓   | 目录公告每条目都是"若干行说明 + 一个处罚档位"排版，被整篇判成档位表（45 块全标 tier_table），`is_catalog` 根本拿不到 |

**最终判据**（全库 103 文件实测零误伤）：

| 文件          | 非空行  | 独占标准号行 | 占比          |
| ----------- | ---- | ------ | ----------- |
| 2020 认证目录公告 | 4056 | 365    | **9.00%** ✅ |
| 2022 消防产品目录 | 2264 | 127    | **5.61%** ✅ |
| 建筑工程消防验收导则  | 8561 | 13     | 0.15% ❌     |
| 电动自行车建设导则   | 345  | 0      | 0.00% ❌     |
| 其余 99 个文件   | —    | 0      | ~0          |

导则 0.15% vs 目录 5.61%，**差 37 倍**，阈值取 2% 留足安全边际。

关键改进是要求标准号**独占整行**（正则尾部锚定 `$`），这样"句内引用"  
匹配不上。

### 3.3 一个检测器改 5 版才收敛

**问题**：想统计"模型有多少次弃答"，用来区分"检索差"和"模型不肯答"。  
最初只匹配字面 `"检索内容不足"`，结果漏掉换了措辞的弃答。

**五次迭代**：

| 版本     | 做法                 | v6 结果     | v7 结果     | 失败原因                             |
| ------ | ------------------ | --------- | --------- | -------------------------------- |
| v1     | 只匹配一个短语            | 漏 20      | 漏 4       | 换个措辞就漏                           |
| v2     | 12 类否定模式组          | **误报 29** | **误报 29** | 新 prompt 让**正常答案**结尾也写"检索内容未覆盖…" |
| v3     | 加"必须无 [片段N]"       | 漏 9       | 漏 8       | 弃答答案里标注满天飞                       |
| v4     | 看 [片段N] 后 30 字有无否定 | 0.809     | 0.851     | 窗口怎么调都翻车                         |
| v5     | 只看开头 60 字          | 0.957     | 0.787     | 正常答案开头也有法定表述                     |
| **v6** | **LLM judge**      | —         | —         | —                                |

**最终结论**：

> **弃答是语义判断，不是字符串匹配。**  
> 同一个意思能被写成十几种说法，而正常答案里也随时出现否定词。  
> 词法规则在这件事上只会无限震荡。

改为复用项目已有的 LLM judge 基础设施，与四个 RAGAS 指标同一套口径。  
词法版降级为无 API Key 时的兜底（实测漏判 0，可安全降级）。

**这个过程的产出不是那个函数，而是"我知道什么时候该停止调参"。**  
v5 之后准确率还在 0.787~0.957 之间震荡，我就没有继续加第 6 版规则。

### 3.4 工程化补齐

| 能力                  | 说明                                                                                                         |
| ------------------- | ---------------------------------------------------------------------------------------------------------- |
| **索引同步自检**          | `build_index.py` 启动时检查索引元数据是否含新分块标记。改了分块策略但没重建索引，是最隐蔽的坑（表现是"分数完全不变"）                                       |
| **多 provider 故障转移** | LLM 主备链，13 个业务文件零改动                                                                                        |
| **人工修改检测 Agent**    | 对比改动前后的文件，自动生成变更报告，定位原因并给出解决方案                                                                             |
| **Embedding 选型与迁移** | 从本地 Ollama（3841 chunk 需 3 小时+）切到阿里云 `text-embedding-v4`（26.9 块/秒），**维度 1024 与原 FAISS 索引完全一致，换 API 无需重建索引** |

### 3.5 测试里踩的坑也值得讲

我写的测试第一版把 `common.config.get_settings` 换成 lambda，导致  
`test_router` 失败 —— 因为 `common/router.py` 在模块顶层 import 了它，  
而那个测试依赖它的 `@lru_cache`（用 `monkeypatch.setenv` + `cache_clear()`  
验证 `ROUTE_MAX_HOPS` 生效）。

**跨文件污染**。正确做法是 `common.config` 保持原样，只替换被测模块自己  
import 进来的符号。这条边界已写进测试文件头。

## 四、面试时可以主动讲的三个点

如果时间有限，我建议重点讲这三个 —— 它们比"用了 LangGraph"更能体现能力：

### 1. 我如何区分"策略无效"和"代码没执行"

改了两轮分块策略，评测分数**纹丝不动**。当时以为是策略无效，  
排查半天才发现是**重建命令参数写错，索引从未重建**。

现在 `build_index.py` 会在重建完成后直接报告落库的实际标记数：

```
分块标记：is_catalog=268  is_tier_table=9
```

**"效果完全不变时，先确认代码是否真的执行，再分析策略。"**  
这听起来是常识，但我在生产项目上真的踩过。

### 2. 我会主动推翻自己的假设

我原本认为"让模型少弃答会换来幻觉上升"，所以在 prompt 里保留了严格的  
弃答条件。实测 47 条：**弃答从 34 降到 11，faithfulness 一条没掉**。

假设错了就改，数据说话。这比"我设计了一个很严谨的方案"有说服力得多。

### 3. 我知道什么时候停止调参

弃答检测器调了 5 版还在震荡时，我停下来换了思路（词法 → 语义），  
而不是继续加第 6 条规则。

另一个例子：目录条目切分的覆盖率公式，我试了"基数惩罚"和"topN 稀有词"  
两种方案。topN 方案在 3 条样本上把排名从 4 提到 2，看起来有效 ——  
但我**没有采用**，因为只有 3 条样本、调参依据不足。

## 五、技术选型说明（可能被追问的点）

**为什么用 FAISS 而不是 Milvus？**  
两者都支持。默认走 FAISS（本地文件、无外部依赖、便于开发和评测）；  
Milvus 后端已实现并保留（`--backend milvus`），生产环境数据量大时切换。  
Embedding 维度在配置里有显式警告，换模型必须核对，否则索引维度不一致会检索错乱。

**为什么 Embedding 选阿里云 text-embedding-v4？**

- 维度 1024，与既有 FAISS 索引**完全一致** → 换 API 无需改索引维度
- 中文语义检索专项优化，匹配法律条文场景
- 前 1000 万 token 免费（一次全量重建足够）
- 提供 OpenAI 兼容端点，现有代码零改动
- 性能：3.04s/chunk → 0.037s/chunk（约 80 倍）

**为什么规则精排要用 IDF 加权覆盖率？**  
实测发现 BM25 把正确答案排第 1，但重排后被挤出 top-k。根因是覆盖率  
在"比谁复述查询里的烂大街词更多"：答案块命中"电线电缆"这类稀有词，  
噪声块复述"消防/产品/目录/认证"这类高频词。

改为按 IDF 加权后，语料 3990 条里"消防"几乎处处都在（命中不构成相关性证据），  
而"电线电缆"只出现在 12 条里（命中一次就是强证据）。

## 六、诚实的局限

面试时主动说出局限，比被追问出来更好：

1. **context_recall 仍偏低（0.548）** —— 主要卡在跨文档综合类  
   （recall 0.512），需要多跳检索或查询分解，我还没做。
2. **陷阱题 prec 仅 0.100** —— 目录类问题的噪声过滤仍不够精细。
3. **评测集 47 条偏小** —— 置信区间较宽，我知道这一点，所以在结论上  
   保持了克制（比如拒绝在 3 条样本上调参）。
4. **LLM 故障转移尚未在真实故障下完整验证** —— 单元测试覆盖了 24 种场景，  
   但 DeepSeek 恢复后需要再跑一次同模型的评测，才能对齐"策略效果"与  
   "模型差异"。
