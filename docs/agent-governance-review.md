# Agent 治理评估 · 工具调用与记忆分层

> 评估对象：本项目（消防智能执法多 Agent 系统）
> 评估输入：一份关于「AI Agent 工具调用治理」的通用方法论
> 评估日期：2026-10-29

---

## 摘要（先说结论）

那份方法论讲的是**「让 LLM 自由选择并调用工具」**的 Agent 形态下的治理问题。
本项目**不是那种形态** —— 它是确定性编排（LangGraph 固定流程 + 显式路由），
LLM 不负责选工具，只负责在给定上下文里生成文本。

所以那份方法论的 8 个治理点里：

| 治理点 | 适用性 | 结论 |
|--------|--------|------|
| ① 工具标准化 Schema 约束 | 🟡 部分 | MCP 工具已有 schema；**高危操作无分级** |
| ② 工具分类隔离 | 🔴 缺失 | 高危操作与普通操作无区分 |
| ③ 工具权限白名单 | 🔴 缺失 | 任何有效 Token 都能执行高危操作 |
| ④ 前置意图校验 | 🟢 已具备 | 三级级联路由已有 |
| ⑤ 调用频次限流 | 🔴 缺失 | 无工具级频次限制 |
| ⑥ 结果后置校验 | 🟢 已具备 | 片段质量过滤 + 改动检测已有 |
| ⑦ **高危二次确认** | 🔴 **缺失（最严重）** | **已实现，见下** |
| ⑧ 重复调用检测 | 🟡 部分 | 审批幂等有；工具级重复无 |

**记忆分层机制的结论：不需要引入完整机制，但发现并修复了一个真实的串台隐患。**

---

## 一、为什么大部分治理点不适用

### 本项目的 Agent 形态

```
用户请求
   ↓
gateway 路由（规则 → 分类器 → LLM 三级级联）    ← LLM 不选工具，只判断意图
   ↓
固定编排（LangGraph 节点 / 显式端点调用）
   ↓
具体能力（检索 / 抽取 / 生成 / 识别）
```

关键区别：

| | 工具调用型 Agent | 本项目 |
|---|---|---|
| 谁决定调什么 | **LLM 自己选** | **代码固定** |
| 工具数量 | 十几个，LLM 要挑 | 4 个服务，路由已定 |
| 工具描述的作用 | 决定 LLM 选对工具 | 只影响意图分类 |
| 参数填错 | LLM 幻觉填错 → 接口报错 | 代码写死，无此风险 |
| 死循环 | LLM 反复调同一工具 | 流程固定，无循环 |

**所以「模型会乱调用工具」这个前提在本项目不成立。**

方法论里那句「模型永远会犯错，必须靠工程兜底」是对的，
但本项目的工程兜底已经做在了**别的位置**：

| 方法论说的兜底位置 | 本项目实际的位置 |
|---|---|
| 工具 Schema 校验 | **路由前的意图分类**（三级级联） |
| 工具权限白名单 | **JWT claims + 检索层过滤**（dept/clearance/valid_until） |
| 调用频次限流 | `route_max_hops=3`（路由级联深度上限） |
| 结果后置校验 | `_is_useful` 片段过滤 + `change_detector` 改动检测 |

**结论：治理点不是「缺失」，而是「落点不同」。**

## 二、真正缺失的部分（已实现）

### 高危操作二次确认 🔴 → ✅

**这是唯一一个既适用、又确实缺失、且后果严重的点。**

#### 原实现的问题

`POST /api/doc/review/{review_id}/approve` 会检测人工改动、
统计 `high_risk_count`，然后：

```python
high_risk = sum(r.get("high_risk_count", 0) for r in change_reports ...)
# ↓ 移动文件、标记 approved、写状态
# ↓ 之后才在返回消息里写：
"；检测到 N 处高风险改动，请管理员复核报告"
```

**文书已经被归档成终稿了，那句「请复核」只是个事后提示。**

在执法场景里，高风险改动可能涉及「法律依据」「处罚金额」这类关键字段 ——
它们决定的是执法文书能不能站得住。

#### 现在的实现

```
approve(review_id, confirm_high_risk=false)
   ↓
检测改动 → 统计 high_risk_count
   ↓
high_risk > 0 且未确认？
   ├─ 是 → status="confirmation_required"
   │        ★ 一个文件都没动过
   │        返回改动报告详情，人工确认后带 confirm_high_risk=true 重来
   └─ 否 → 移动文件到 official/，标记 approved
```

三个关键设计：

1. **拦截而非提示**。提示会被忽略，拦截才会生效。
2. **先判断后移动**。第一版写的是「移动 → 拦截 → 回滚」，
   但回滚可能失败（磁盘满、权限变更、并发），
   会导致文书停在 `official/` 而状态是 `pending` 的不一致。
   现在拦截时根本没动过文件，不需要回滚。
3. **只在有高风险时才拦**。正常文书直接批准 ——
   否则运营会习惯性勾选确认，机制就白做了。

#### 验证

`tests/test_high_risk_confirmation.py`（9 项）验证三个不变量：

- 有高风险 + 未确认 → 文件**仍在 pending/**，状态仍 `pending`
- 有高风险 + 已确认 → 移到 `official/`，状态 `approved`
- 无高风险 + 未确认 → 直接批准

外加两个代码层断言（确认判断在移动之前、thread_id 唯一）。

## 三、记忆分层机制的评估

### 方法论里说的三层隔离

> 会话寻址规则 + 存储分区策略 + 全局共享内存开关
> —— 并不是 Agent 天生自带记忆隔离能力

### 本项目的实际情况

**没有对话记忆机制。** 全库检索 `session_id` / `memory` / `记忆`，
业务代码零命中。项目是**单任务型**（一个案件一次问答 / 一次文书生成），
不是多轮对话型。

但有一个**状态持久化**机制：LangGraph 的 `SqliteSaver` checkpointer。

```
logs/checkpoints.sqlite    thread_id = conversation_id
```

这本身就是「会话寻址 + 存储分区」—— 按 thread_id 存取状态，
不同会话的状态物理隔离。

### 但发现了一个真实的串台隐患 🔴 → ✅

```python
# 修复前
conv_id = conversation_id or f"task_{int(time.time())}"
```

`int(time.time())` 是**秒级**精度。两个并发任务在同一秒发起，
会拿到**完全相同的 thread_id** → checkpointer 按 thread_id 存取 →
第二个任务从第一个的 checkpoint 恢复 → **状态污染**。

执法场景下这不是小问题：两个不同案件的案情要素可能互相污染，
进而影响文书内容。

**修复**：

```python
conv_id = conversation_id or (
    f"task_{int(time.time())}_{uuid.uuid4().hex[:8]}")
```

时间前缀仅供人工排查，唯一性由 uuid 保证。

### 结论

| 问题 | 回答 |
|------|------|
| 需要引入完整的记忆分层机制吗？ | **不需要** |
| 理由 1 | 项目是单任务型，不是多轮对话型，没有跨会话记忆需求 |
| 理由 2 | checkpointer 已按 thread_id 隔离，本就是分区存储 |
| 理由 3 | 全局共享内存开关在这类无记忆架构里无对象可控制 |
| 但—— | thread_id 精度隐患是真的，已修复 |

**如果将来要加多轮对话**（比如「这个处罚怎么算的？再算一下」这种追问），
那时才需要完整的记忆分层，而且要按这个顺序做：
先会话寻址（thread_id 严格隔离）→ 再存储分区（按用户/案件分区）→
最后才考虑共享内存开关（且必须显式关闭跨案件写入）。

## 四、其余治理点的现状与建议

| 治理点 | 现状 | 建议 |
|--------|------|------|
| ① Schema 约束 | MCP 工具由 SDK 自动生成 schema | 保持。**但** MCP 工具应按风险分级标注 |
| ② 工具分类隔离 | 高危操作（approve/reject/prune）与查询混在一起 | 短期靠二次确认兜住；中期给端点打 `risk` 标签 |
| ③ 工具权限白名单 | `require_internal_token` 统一校验，不区分操作 | **建议**：审批类端点要求更高角色（`role=reviewer`） |
| ⑤ 调用频次限流 | 无 | **建议**：对 LLM 端点加 token 预算限流（`BudgetTracker` 已有，需接到线上路径） |
| ⑧ 重复调用检测 | 审批幂等有；工具级无 | 优先级低 —— 流程固定，天然不易重复 |

### ③ 的具体建议（未实现，留给后续）

现在所有 `/api/*` 端点用同一个 Token 校验：

```python
_: None = Depends(require_internal_token)
```

建议改为按操作分级：

```python
# 高危操作要求 reviewer 角色
def require_reviewer(user: UserCtx = Depends(get_current_user)):
    if user.role not in ("reviewer", "admin"):
        raise HTTPException(403, "审批操作需要复核人角色")
```

理由：审批 = 文书从草稿变终稿，等于执法文书生效，
这在制度上应该有权限分离（生成人不能自己审批自己的文书）。

## 五、这个评估本身的方法论价值

这份评估的产出不是「加了多少机制」，而是：

1. **区分了「治理点缺失」和「治理点落点不同」** ——
   8 个点里 6 个「不适用」或「已由别的机制覆盖」，
   1 个真缺失（已补），1 个部分缺失（给了建议）。

2. **拒绝机械照搬**。如果按那份方法论逐条实现，
   会给本项目加上一堆针对「LLM 乱选工具」的防护 ——
   而本项目根本不让 LLM 选工具。
   那是**为了看起来完备而增加无用复杂度**。

3. **找到了一个方法论没提、但更严重的隐患**：
   `thread_id` 秒级精度。
   方法论讲「怎么隔离记忆」，但没讲「隔离键本身会不会撞」。
