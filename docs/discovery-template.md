# Discovery 调研模板 · FDE 交付前置

> **Discovery 是 FDE 与普通开发岗最本质的区别。**
> 开发岗的交付物是代码，FDE 的第一个交付物是**搞清楚该做什么**。
> 这份文档既是模板，也是我自己在消防这个场景上填过一遍的示例。
>
> 用法：接新客户时复制一份，逐节填写。
> **填不满的节就是最大的风险项** —— 不知道就标"待确认"，别猜。

---

## 1. 业务背景

### 1.1 业务目标

- **现在最痛的点是什么？**
- **这个问题造成了多少损失？**（人力成本 / 时间 / 事故 / 投诉）
  > 没有数字就不要往下走。无法量化的问题，交付完也无法证明价值。
- **谁是使用者？**（执法队员？文书人员？领导？）不同角色的诉求差别很大
- **谁是决策者？**（技术部门？业务部门？一把手？）

### 1.2 业务流程

画出当前流程，标注：
- 哪些环节是重复劳动
- 哪些环节依赖少数人的经验（会成为 AI 替换的切入点）
- 哪些环节必须人工（涉及法律效力的环节，AI 只能辅助）

> **本项目示例**：消防文书生成 → 人工审核 → 归档。
> 人工审核这一步不能删（文书有法律效力），但可以做"AI 标出高风险改动，
> 审核人重点看"—— 这是 `change_detector.py` 的设计依据。

### 1.3 合规与监管

| 问题 | 答案 |
|------|------|
| 数据能否出内网？ | |
| 有无等保/密评要求？ | |
| 是否涉及个人信息？ | |
| 法规依据是否会被引用为证据？ | |

> **本项目示例**：消防执法文书有法律效力，AI 的定位必须是"辅助"不是"替代"。
> 这个定位一旦搞错，整个项目方向就错了。

### 2.2 数据可用性评估（最容易被跳过、也最容易致命）

| 数据类型 | 是否存在 | 格式 | 质量 | 可获取方式 |
|---------|---------|------|------|-----------|
| 历史文书 | | | | |
| 法规/标准 | | | | |
| 业务知识 | | | | |
| 历史问答 | | | | |

**逐项判断标准：**

- **质量**：这份数据直接喂给检索，效果会是什么样？
  有没有试过抽样看过 10 条？
- **可获取方式**：谁能给？要走什么审批？多久能拿到？
  > "客户说有数据"和"能拿到数据"之间往往隔着三周审批。
- **格式**：PDF 扫描件需要 OCR；表格需要结构化；纯文本最省事。
  **格式直接决定工作量，评估阶段就要看清楚。**

> **本项目示例**：
> 消防法规原文是扫描版 PDF（需要 OCR + 版面还原），
> 规范化的条文数据需要额外整理。
> 这部分工作量在评估阶段被低估过，导致排期延后 —— 教训是**必须先实际打开 10 份文件看看**。

### 2.3 环境与约束

- 部署环境：内网 / 公有云 / 混合
- 是否允许调用外部 API（数据出境风险）
- 客户已有的基础设施能复用多少

> **"为什么没选备选"这一列是面试重点。**
> 只说"我选了 A"是执行者的说法；
> 能说清"我没选 B 是因为 C"才是做决策的人的说法。

### 4.2 架构

画图 + 文字说明：
- 组件划分与职责
- 数据流
- 失败时怎么降级（**这一条经常被漏，而它是交付质量的核心**）

### 4.3 风险与对策

| 风险 | 影响 | 概率 | 对策 | 责任方 |
|------|------|------|------|--------|
| 数据质量不达标 | 高 | 中 | 先做数据评估再定方案 | |
| 模型效果达不到预期 | 高 | 中 | 分阶段上线 + 人工兜底 | |
| 客户无法配合 | 中 | 高 | 提前明确配合事项并书面确认 | |
| 政策/合规变化 | 高 | 低 | | |

> **"客户无法配合"这一项要单独列。**
> 它是实施项目最大的隐性风险，而且是**唯一完全不由技术方控制**的风险。

## 附：本项目（消防场景）的 Discovery 示例

作为填写参考，把关键几节填好的样子列在这里。

### 业务目标

> **问题**：消防执法文书高度模板化，但每个案子都要人工从零填写，
> 一次文书制作 40-60 分钟，且新人容易出错。
>
> **损失**：按 1 个区县 50 名文书人员、人均日均 4 件文书计算，
> 每月 3000 件 × 50 分钟 ≈ 2,500 小时/年。按人均时薪 150 元计，
> 约 **37.5 万元/年**的人力成本。
>
> **AI 的定位**：辅助而非替代。文书有法律效力，最终审核必须人工。
> AI 承担「初稿生成」与「改动风险标注」，人集中在「高风险项确认」。

### 数据可用性

| 数据 | 现状 | 结论 |
|------|------|------|
| 消防法规原文 | 扫描版 PDF | 需 OCR + 版面还原，**工作量最容易被低估** |
| 文书模板 | 7 份 .docx | 结构清晰，可直接用 |
| 历史文书 | 零散，不成体系 | **不足以做微调，只能做检索增强** |
| 历史问答 | 不存在 | 无法用真实数据评估效果 |

> **关键判断**：因为没有历史问答数据，
> 效果评估只能靠**人工构造测试集**（47 条分类标注的测试样本）。
> 这个局限性在汇报时必须主动说，不能等客户问出来。

### 明确不做的事

- 不做自动审批（法律效力要求人工签字）
- 不做跨部门系统对接（本期不含）
- 不做移动端（执法现场用平板的场景下优先级低）

### 最大风险

> **客户提供的法规 PDF 质量不达标** —— OCR 后条文错漏，
> 导致引用了错误的法条。
>
> 对策：上线前用 100 条抽样人工核对 OCR 结果；
> 同时保留原文链接，AI 输出必须能溯源到原文页码。
>
> 这一条已落到 `change_detector.py` 的风险分级逻辑里：
> 涉及「法律条款」的改动自动标为高风险，强制人工确认。
