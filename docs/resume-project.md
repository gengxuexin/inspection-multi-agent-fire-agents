## 300 字版

> **消防执法智能辅助系统｜个人项目｜Python / FastAPI / LangChain / FAISS**
>
> **背景**：消防执法文书高度模板化，每次制作 40~60 分钟且易出错，
> 属典型的高人力成本、低技术门槛场景。
>
> **架构**：网关（鉴权/限流/熔断）+ 法规服务（RAG 问答与文书生成）+
> 语音服务（ASR/TTS）+ 视觉服务（YOLO + OCR）四服务编排，
> 34 个 API 端点，docker-compose 一键部署，7 个容器全部健康检查通过。
> 检索侧采用 BM25 + 向量 + RRF 融合召回与 IDF 加权精排；
> 文书生成引入弃答判断与审批流，涉及法条的改动自动标记高风险。
>
> **我的主要工作**：
> 1. **建立评测可信度机制**。发现连续三轮 RAGAS 评测的检索结果逐字相同，
>    属空跑，而分数差异实为 LLM 判分抖动（实测 0.021）。
>    据此建立上下文指纹（不含答案与分数）、空跑阻断与噪声底机制，
>    使优化结论可归因。相关代码 30 个单元测试覆盖。
> 2. **三轮精排 A/B 实验**。定位并修复"改一个 IDF 上限常量同时影响
>    BM25 召回与精排排序"的问题（拆分两者），通过候选池重叠度分析
>    证明变量隔离失败；最终因跨文档类召回下降而回退效果部分，
>    保留结构改进。
> 3. **发现并治理引用编造**。实测 10 个问题仅 20% 的法条引用
>    可溯源至检索结果，故建立溯源检测与三道防线
>    （生成约束/审核标记/归档确认）。
> 4. **生产化**：三态熔断、token 预算、11 项 Prometheus 指标与
>    19 面板 Grafana 看板；编写 50+ 个验证脚本（6,500+ 行）覆盖
>    依赖一致性、容器导入路径与指标高基数防护。

## 写简历时的几条判断

### 1. 要写"我做了什么判断"，不要写"我用了什么技术"

对比：

| ❌ 技术罗列 | ✅ 判断展示 |
|------------|------------|
| 使用 BM25 + 向量混合检索 | 通过候选池重叠度分析发现变量隔离失败，定位到共享常量 |
| 集成 Prometheus + Grafana | 建立指标高基数防护，避免每个 id 生成新时间序列 |
| 实现 RAG 问答 | 建立空跑检测与噪声底机制，使优化结论可归因 |
| 用 LangChain 构建链路 | 发现弃答判定不是代码函数而是 prompt 约定，据此改三态 |

技术栈任何人都会写，**判断力才是差异**。

### 2. "优化了 X%"不如"发现 X 是错的"

前者是执行者的描述，后者是决策者的描述。

而且后者更安全 —— 前者被追问"怎么测的"就崩，
后者被追问你正好有话可说。

### 3. 失败经历要写成"发现"，不是"犯错的经历"

- ❌ "我犯了个错误，三轮评测全跑了空跑"
- ✅ "发现连续三轮评测的检索结果逐字相同，属空跑，据此建立三道机制"

同样的事实，后者体现的是**发现问题的能力**。

### 4. 不要写"精通"

写"熟练使用"或干脆不写。
技术列表真正起作用的是**和后面的判断配对**，
孤立的技能词没有说服力。

而它恰好是这个项目的重心。

## 常见追问的简历速答

**Q：你在这个项目里最大的贡献是什么？**
> 不是某个功能，是建立了一套让优化结论可信的机制。
> 因为我发现之前的优化里有一半是空跑——
> 有结论说不清归因，所以后面所有优化都先要过这道验证。

**Q：如果只用一句话概括，会说什么？**
> 学会了在优化之前先验证测量方法本身是有效的。

**Q：为什么这个项目不是团队项目？**
> 确实是一个人做的。但我刻意按交付标准做——
> 有测试、有监控、有文档、有成本测算，
> 而不是"跑通就行"。这也是我下一个岗位想继续做的事。
