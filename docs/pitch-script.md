# 项目自述口播稿

> 三个长度，按面试官给你的时间选。
> **不要背** —— 记住结构和几个关键数字即可，说错了比忘词更糟。

---

## 版本 A：90 秒（自我介绍里用）

> 我做了一个消防执法的智能辅助系统。
>
> 背景是消防执法文书高度模板化，但每个案子都要人工从头填，
> 一次文书制作 40 到 60 分钟，新人也容易出错。
>
> 系统分四层：网关做鉴权限流和熔断，法规服务做 RAG 问答和文书生成，
> 语音服务做 ASR/TTS，视觉服务做 YOLO 检测和 OCR。
> 语料是 103 份消防法规文档，切成 4019 个语义分块。
>
> 我在这个项目里做得最多的事是**用可量化的评测驱动优化**，
> 但真正的收获是——**测量方法本身会骗人，而且骗我的方式很朴素**。
> 我曾经连跑三轮评测，分数有涨有跌，写了优化结论；
> 后来逐条比对才发现三轮的检索结果逐字完全相同，是空跑。
>
> 这件事之后我给每一步都加了验证机制，
> 所以我现在能说的是"这个改动有没有用"，
> 而不是"我感觉有提升"。具体我可以展开讲。

**为什么这样讲**：
- 30 秒讲清项目规模与技术栈
- 30 秒给出**不一样的**记忆点（评测驱动 + 方法论）
- 留一个明确的钩子（"我可以展开讲"），让面试官选择深挖方向

## 版本 B：5 分钟（技术深挖面用）

> ## 1. 项目是什么（40 秒）
>
> 消防执法的智能辅助系统。解决的是文书制作效率低的问题。
>
> 四个服务：网关负责鉴权、限流、熔断；法规服务做 RAG 问答和文书生成；
> 语音和视觉服务做多模态输入。
> 语料 103 份法规文档、4019 个语义分块，
> 检索用 BM25 加向量检索的混合方案，34 个 API 端点。
>
> ## 2. 我的核心工作：评测驱动的优化（90 秒）
>
> 一开始我按常规做法调检索策略，跑评测看分数。
> 跑了三轮之后我把三轮的上下文逐条比对——
> **发现三轮的检索结果逐字完全相同。**
>
> 检索层压根没变，而分数有涨有跌。
> 后来我做了个对照实验测出LLM 打分的抖动是 0.021，
> 而我当时观察到的变化是 0.004 到 0.021，全在抖动量级以内。
>
> 最麻烦的是我**已经把那个错误结论写进文档了**，
> 而那份文档后来成了我面试讲的素材。
>
> 之后我补了三道机制：
> 第一是**上下文指纹**——只哈希检索结果，不含答案和分数；
> 第二是**空跑检测**——指纹一致就直接阻断，不让结论写出去；
> 第三是**噪声底**。
>
> 噪声底这里有个细节：我最初设成 0.02，就是实测抖动那个量级。
> 结果有个差值恰好是 0.021，卡在边界上，测试直接失败了。
> 后来才明白**单次 A/B 差值只是抖动幅度的下界，不是幅度本身**，
> 差值分布有方差，两次恰好接近不代表常态如此。现在用 0.10。
>
> ## 3. 一个技术判断：局部改进可能伤害整体（90 秒）
>
> 有了可信的测量之后，我做了三轮精排优化的 A/B。
>
> 第一轮我改了三个地方：IDF 上限从 3.0 放宽到 8.0、
> 加权从线性改成平方、疑问句折扣。
> 结果 context_precision 涨了 0.021，recall 掉 0.063。
>
> 我先怀疑是精排算错了，做了四个变体的隔离实验，
> 发现每个变体排序都正常——说明覆盖率本身没问题。
> 查候选池重叠度的时候才看明白：
> 只有 17% 的样本检索结果没变，**检索阶段就变了**。
>
> 原因是我改的那个 IDF 上限是个类属性，
> 而那个字典在构建 BM25 的时候就定型了，精排复用的是同一份。
> **我以为在改精排，实际上同时改了召回和排序。**
>
> 更意外的是我把两者拆成独立参数、BM25 还原之后，
> recall 掉得更多，0.085。所以我最初的猜测也错了。
>
> 最后定位到的真因是：平方加权让"命中一个稀有词"压过"命中多个常见词"。
> 这对查单条法条是对的，但跨文档综合类问题的答案分散在多个文件里，
> **每个片段都只命中一个词**，于是全被压下去了。
>
> 这不是 bug，是取舍。而跨文档类占了样本的 45%，
> 代价大于收益，所以我把效果那部分回退了，
> **保留了 IDF 上限拆分这个结构改动**——
> 今后调精排不会连带影响召回。
>
> ## 4. 一个业务发现（60 秒）
>
> 我做了一个演示页，把检索链路每一步的耗时和命中片段都展示出来，
> 打算现场演示"我们的系统引用准确、可溯源"。
>
> 结果做溯源核对的时候发现不对：
> 问"消防救援机构有哪些职责"，
> 答案引用了第四条、第四十五条、第五十三条，
> 但检索返回的五个片段里一个都没有。
>
> **三个条款号全是编的。** 十个问题跑下来可溯源率 20%。
>
> 我一开始以为是自己匹配逻辑的问题，查了 markdown 格式、
> 简繁体差异，最后才确认是模型真的在编。
>
> 消防执法文书有法律效力，编造的条款号会直接影响法律适用。
> 所以我配套了三道防线：生成时 prompt 显式约束、
> 审核时用 MCP 工具把涉及法条的改动自动标为高风险、
> 归档前强制人工确认。**溯源检测就是第一道防线的验证手段——
> 没有它，根本不知道它在编。**
>
> ## 5. 收尾：我的收获（40 秒）
>
> 项目做完，技术上的东西反而不是记得最牢的。
>
> 我记住的是：**每一次问题都是同一类**——
> 三轮空跑、共享常量、优雅降级藏起依赖缺失、
> 连我的验证脚本自己都出过 bug。
> 都是"我以为我知道自己在做什么，其实不知道"。
>
> 所以我做的事就是给每一步加验证。
> 这些机制的价值不在于"防止出错"，
> 而在于**一旦出错能立刻知道**，
> 而不是拿着错误结论继续往下走。

## 版本 C：10 分钟（面试官说"详细讲讲"时）

在版本 B 基础上，按追问方向展开。**每段都是独立的模块，可以只讲被问到的那块。**

### 模块 A：RAG 检索侧

| 层次 | 我做的 | 关键认知 |
|------|--------|---------|
| 分块 | 按目录结构切，产出 4019 个分块 | 分块策略必须先问："切出来的更好片段，精排会不会把它排上去？"——我踩过这个坑 |
| 召回 | BM25 + 向量 + RRF 融合 | 两路各有盲区：BM25 认字面、向量认语义 |
| 精排 | IDF 加权覆盖率 + 结构匹配 + 长度惩罚 | 覆盖率一开始是 bool 命中，导致 10~32 个候选并列满分，BM25 的判断被抹平 |

**可讲的坑**：
1. `if t in text` 是 bool 命中，命中 1 次和 5 次同权 → 覆盖率饱和
2. 改成 tf 饱和递增后更糟——法条文本里重复的往往是虚词，
   实测噪声片段 `tf={'消防设施':1, '包括':7, '建筑':4}`，
   光靠"包括"重复 7 次就刷到 0.85 分。**重复次数不是相关性的证据**
3. IDF 上限 3.0 对 4019 片段太紧——log(4019)=8.30，
   **df<200 的词全被压成 3.0**。实测"电线电缆"（df=12，答案词）
   和"属于"（df=123，噪声词）权重完全相同，**IDF 加权等于没加**

### 模块 B：评测可信度

| 机制 | 做法 | 为什么 |
|------|------|--------|
| 上下文指纹 | sha256(question + contexts)，16 位截断 | **绝不含答案和分数** —— 含了分数一变指纹就变，空跑检测立刻失效 |
| 空跑检测 | 指纹一致 → 阻断，不让结论写出去 | 误报代价只是多跑一次；漏报代价是写出错误结论 |
| 噪声底 | 0.10（实测抖动 0.021 的约 4.8 倍） | 单次差值只是抖动幅度下界 |
| 可比性检查 | 样本数 + top_k 必须一致 | v8 的 cp 从 0.520 掉到 0.325，**纯 top_k 5→8 造成的**，不是检索退化 |

### 模块 C：生产化

| 项 | 做法 | 踩过的坑 |
|----|------|---------|
| 部署 | 4 服务 + Redis + Prometheus + Grafana，compose 一键起 | 端口冲突（本地 8000 被占，**且不只一处**，redis 的 6379 又被另一套项目占）；uid 不匹配（挂载目录属主 1000，容器内 appuser 是 10001） |
| 健康检查 | `/health` 存活 + `/ready` 依赖就绪 | 挂载的模型权重没到位时 `/ready` 报 degraded，这是**正确行为**——能返回 200 不等于能干活 |
| 弹性 | 三态熔断器 + token 预算 + 超时 | 故障损失比 API 费高 60 倍，这是做熔断的成本依据 |
| 可观测 | 11 个指标 + 19 面板 5 分组看板 | 指标标签必须做高基数归一化，否则每个 id 都生成一条新时间序列 |

### 模块 D：MCP 与工具化

- 把改动检测能力封装成 MCP 工具（3 工具 + 2 资源 + 1 提示）
- **踩了两个 SDK 版本坑**：MCP 2.x 把 `FastMCP` 改名 `MCPServer`
- 端到端测试抓到真 bug：`analyze_changes` 写到 `output/change_reports/`，
  而工具去 `output/reviews/` 找——
  **`compare_documents` 返回成功还给了 json_path，但 `list_reports` 永远返回 0**
- 教训：**调用成功 ≠ 功能可用。** 只测"函数能调通"发现不了这类问题

### 模块 E：成本（TCO）

| 场景 | 人力 | 基础设施 | 故障损失 | LLM |
|------|------|---------|---------|-----|
| 小型试点（30 用户）| **73.7%** | 9.4% | 16.6% | **0.2%** |

结论：**AI 替代的是人力，不是 API 调用。**
客户付的不是"买 API"，是"少雇一个人"。

**故障损失比 API 费高 60 倍** —— 这是"为什么做熔断降级"的成本依据，
不是"熔断听起来专业"。

成本结构在月请求超百万时会翻转：从"人力主导"变成"调用量主导"。

## 讲法上的几条硬规矩

### 1. 主动讲失败，但一定要带上解决

只讲"我错了"是自我贬低，讲"我发现 + 我加了机制"才是能力展示。

每个故事的收尾都是："所以我现在能说的是 XXX，而不是 YYY"。

### 2. 数字要能追问出下一层

说"可溯源率 20%"，要能立刻回答：
- 怎么测的？（答案里抽条款号 → 中文数字转整数 → 在检索片段里比对）
- 为什么低？（检索目标"包含相关内容"，生成需要"能构成完整答案的依据"）
- 怎么补？（三道防线 + 溯源检测作为验证手段）

**记错数字比不记得更糟** —— 对方会顺着追问。

### 3. 不确定的就说不确定

比如"可溯源率 20%"这个数：
- 10 个问题、每条引用几个条款不固定
- 同一问题两次跑结果不同
- 所以它是个**量级参考，不是精确指标**

主动说清这一点，比给个看起来精确的数字可信。

### 4. 别把工具数量当成就

我写过 55 个验证脚本、6,751 行。但我不会说"我写了很多工具"——
我会说"**因为不写工具验证自己，我根本不知道自己的优化有没有用**"。

后者才是逻辑，前者听起来像在凑数。
