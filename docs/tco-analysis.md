## 一、结论先行

**这个系统在小到中等用量下，成本由人力主导而非 API 费用主导。**

| 场景 | 用户 | 月请求 | LLM/月 | 总成本/月 | 年成本 |
|------|------|--------|--------|-----------|--------|
| 小型试点 | 30 | 9,000 | 32 元 | 12,207 元 | **14.65 万** |
| 区县规模 | 300 | 180,000 | 612 元 | 31,492 元 | **37.79 万** |
| 市级规模 | 2,000 | 1,500,000 | 5,094 元 | 165,424 元 | **198.51 万** |
| 省级规模 | 8,000 | 7,200,000 | 24,447 元 | 589,777 元 | **707.73 万** |

小型试点的成本构成：

```
人力_运维与支持  占比 73.7%  ████████████████████████████████████
故障损失_估算    占比 16.6%  ████████
基础设施        占比  9.4%  ████
LLM_推理        占比  0.2%
Embedding       占比  0.0%
```

**这个反直觉的结论恰恰是最值钱的部分**，理由在第三节。

## 二、口径说明

先说清楚，免得被追问时露怯。

### 价格基线

取自 DeepSeek 2026-08 公告后的现行定价，单位**元 / 百万 token**：

| 模型 | 输入（缓存命中） | 输入（未命中） | 输出 |
|------|----------------|--------------|------|
| V4-Flash | 0.02 | 1 | 2 |
| V4-Pro | 0.025 | 3 | 6 |

**已含峰谷折算系数 1.25** —— DeepSeek 对工作日 9:00–12:00、14:00–18:00 计费翻倍，
这两段占全天 25% 的时间，等效系数 = 0.75×1 + 0.25×2 = 1.25。

> 面试时务必说清"截至哪天的价格"。说"DeepSeek 很便宜"而不给日期，
> 一旦对方知道你用的是哪年的信息，可信度就没了。

### token 消耗

按本项目 RAG 链路的实际阶段划分：

| 阶段 | 输入 token | 输出 token |
|------|-----------|-----------|
| 意图分类 | 180 | 20 |
| query 改写 | 350 | 80 |
| embedding | 60 | 0 |
| rerank | 0 | 0（纯本地） |
| 答案生成 | 2,200 | 600 |

单次请求合计约 **2,790 输入 / 700 输出**。

**缓存命中率按 55% 估** —— 法规 system prompt 很长且固定，
命中缓存后输入成本降到 1/50。
**这是本测算里不确定性最大的参数**，真实值取决于 system prompt 是否稳定、
请求间隔是否够密。

### 不含什么

一次性实施成本（开发/测试/上线）、数据标注、合规审计 —— 这些应该单列，
因为是一次性的，混进年度运行成本会让 TCO 失去意义。

## 三、为什么"API 只占 0.2%"这个结论重要

如果只看到"大模型 API 一年才几千块"，容易得出"这个 AI 项目很便宜"的结论，
然后在实施时给客户报一个无法支撑的价格。

真实的成本结构是：

> **AI 替代的是人力，不是 API 调用。**
> 省下的是 0.5 个运维工程师（9,000 元/月），
> 花的是服务器（1,150 元/月）+ 一点 API 费（32 元/月）。
> 净收益约 8,000 元/月。

这个换算方式决定了两件事：

1. **客户的付费意愿来自哪里。**
   客户付的不是"买 API"，是"少雇一个人"。
   报价应该对着人力成本折算，不该对着 API 成本加成。

2. **成本优化的优先顺序。**
   在中小用量下，把 API 从 1.0 元/百万换成 0.5 元，
   每月省 16 元，占总成本 0.13% —— **几乎没有意义**。
   而把"人工审核环节"再压缩 10%，每月省 900 元，占 7%。

### 成本结构的翻转点

敏感性分析（区县规模，300 用户）：

| 人均日请求 | 月请求 | LLM 费/月 | 占总成本 | 单次成本 |
|-----------|--------|-----------|---------|---------|
| 5 | 45,000 | 154 元 | 0.5% | 0.0034 元 |
| 10 | 90,000 | 307 元 | 1.0% | 0.0034 元 |
| 20 | 180,000 | 612 元 | 1.9% | 0.0034 元 |
| 40 | 360,000 | 1,224 元 | 3.8% | 0.0034 元 |
| 80 | 720,000 | 2,446 元 | 7.3% | 0.0034 元 |

**请求量涨 16 倍，LLM 占比从 0.5% 涨到 7.3%。**

也就是说：**成本模型在极高用量场景下会翻转** ——
从"人力主导"变成"调用量主导"。
当某个客户的月请求量超过百万级时，
节省人工不再是主要杠杆，缓存和模型分流才变成主要杠杆。

> ★ 这个翻转点是**FDE 的核心判断力所在**：
> 知道自己的方案在什么规模下会从"划算"变成"不划算"，
> 以及在那个点上要提前做什么准备。

### 故障损失为什么必须算进去

小型试点里"故障损失_估算"占 16.6%（2,025 元/月），
比 API 费高 60 倍。

算法：按可用性 99.5% 估，月度不可用 3.6 小时，
影响 30 人 × 3.6 小时 ÷ 8 小时 × 150 元/时 = 2,025 元。

**这一项恰恰是"为什么要做熔断和降级"的成本依据** ——
不是"熔断听起来更专业"，而是系统不可用的代价，
比它消耗的 API 费用高两个数量级。

本项目已有三态熔断（CLOSED / OPEN / HALF_OPEN），
在 TCO 里就是这一行的支撑。

## 四、降本措施与投入产出

按投入产出排序（**这个顺序本身就是面试可讲的内容**）：

| 措施 | 说明 | 投入 | 收益 |
|------|------|------|------|
| prompt 缓存 | 法规 system prompt 固定很长，命中缓存后输入成本降到 1/50 | 低 | 最高 |
| 意图分类降级到小模型 | 分类不需要 Pro 档模型，路由准确率要求也没那么高 | 低 | 高 |
| 相似问题结果复用 | 法规问答高度同质，高频问题可命中已有答案 | 中 | 高 |
| 检索 top_k 从 8 降到 5 | 输入 token 直接减 37% | 低 | 中（有精度代价） |
| 自建推理（GPU 常驻） | 替代 API，适合高频稳定负载 | 高 | 视用量，很用量才回本 |

**面试时的正确表述顺序：**

先讲缓存与分流（几乎零投入）→ 再讲自建（要讲清回本临界点）
→ 最后才讲降精度换成本。

只讲"换更便宜的模型"会被追问一句"精度掉了吗"就答不上来 ——
因为降级到小模型确实会掉精度，要说清"分类任务对精度不敏感，
路由错一次只是多调一次工具，而生成任务才必须用好模型"。

## 五、怎么用这份测算

### 客户沟通时

1. 先问清用量（用户数 × 人均日请求）→ 定位到哪个场景档
2. 报人力替代收益，不报 API 差价
3. **主动说清翻转点**：如果您的量增长到百万级/月，
   成本结构会变，届时需要重新测算
4. 把故障成本摊开讲 —— 让客户看到"稳定性的价值"

### 面试时

这是一个能主动展示"FDE 不只是写代码"的抓手。
大部分候选人被问"怎么评估 AI 项目的成本"时只能答"算 token"。

能讲清这四点的人不多：
1. 人力成本才是大头
2. 故障成本比 API 成本高一到两个数量级
3. 成本结构在特定规模会翻转
4. 降本措施的优先级取决于规模

### 局限（主动说，比被问出来好）

- 单价会变，改 `PRICES` 即可重算
- token 消耗随 prompt 版本变化，**改 prompt 后必须重跑**
- 缓存命中率是估算，本测算里不确定性最大的参数
- 人力成本按一线城市估，地区差异较大
- 未含一次性实施成本
