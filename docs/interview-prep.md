# 面试问答准备 —— 预判追问与应答要点

> 每题都给出**核心答案 + 支撑证据 + 可能的追问**。  
> 目标是让回答**可验证**，而不是听起来漂亮。

---

## Q1：介绍���下这个项目

**一句话**：把 103 份消防法规文档、4019 个语义分块做成可追溯问答的 RAG 系统，  
外加多模态案件分析和文书自动生成的编排层。

**规模**：业务代码 19,643 行（94 文件）/ 275 个测试 / 53 个验证脚本（6,504 行）/
47 条人工标注评测集 / 4019 个语义分块。

> ★ 报规模时把"验证脚本"也算进去 —— 这是刻意展示的：
> 这个项目里我写工具的比重不小（6227 行 vs 业务 19643 行），
> 因为**不写工具验证自己，我根本不知道自己的优化有没有用**（见 Q4）。

**主动引导**：这个项目里我做得最多的是**用可量化的评测驱动优化**，  
一共 5 轮迭代、6 次定位，有完整的推理链可以展开。

## Q2：为什么 RAG 不用微调，先做检索优化？

**核心答案**：RAG 和微调解决的是不同问题。法规会变、条文要可追溯、  
答案要标来源 —— 这三点都排除了微调。而且手上没有高质量标注数据做微调。

**追问：那你为什么不训练一个 reranker？**  
我确实用了规则精排替代了交叉编码器。理由是：

- 领域语料只有 4019 个 chunk，训练样本不足以让一个小模型学到可靠的排序
- 规则精排的每一条规则都能解释（条款匹配分级、IDF 加权覆盖、  
  目录降权、查询意图豁免），出问题能定位到具体哪条
- 交叉编码器要引入额外推理延迟，实测延迟换来的 recall 提升不如  
  把精力放在分块边界恢复上

**我的判断是**：先做收益最大、最可解释的部分。如果分块边界修好后  
recall 还上不去，那才是 reranker 真正该上的时机。

## Q3：context_precision 只有 0.221，为什么不用重训 embedding？

**核心答案**：分块边界是当前主要矛盾，embedding 不是。

**支撑**：某条问题里 BM25 把正确答案排第 1 名，但被重排挤出 top-k。  
逐层排查发现答案完整存在于一个 306 字 chunk 里 —— **embedding 检索是好的，  
是分块把答案和无关内容粘在一起了**。

> 检索链路四层：切分 → 向量化 → 召回 → 精排。  
> 我先确认了是哪一层出问题，才决定改哪一层。

**追问：怎么确认不是 embedding 的问题？**  
分层的召回日志：BM25 rank=1（已进 pool=50），向量召回也包含它，  
只是在重排阶段被压下去。同时答案的语义完整性可验证（89 字的独立条目，  
包含完整表述）。

## Q4：你怎么保证优化是有效的，不是过拟合？

**核心答案**：我主动放弃过一次有效但依据不足的优化。

**具体例子**：目录条目切分后答案排名 4/5/1，都进 top5 但勉强。  
我试了"top2 稀有词"覆盖率口径，在 3 条样本上把排名从 4 提到 2 ——  
**提升是真实的，但我没有采用**，因为只有 3 条样本，泛化性未知。

**其他保障**：

1. 47 条评测集按 category / difficulty 分层，避免总分掩盖结构性问题
2. 同一轮迭代内保持评测集不变，只改一个变量
3. 每个新规则都要在**全库 103 文件**上验证无误伤  
   （独占标准号占比：目录 5.61~9.00%，导则 0.15%，差 37 倍）

## Q5：讲一个你觉得最有成就感的改动

**核心答案**：P4 目录条目切分的判据修正。

**为什么有成就感**：三次都改错了，而且错法各不相同 ——

- 第一次：中位间隔阈值。没看真实数据，定了个"看起来合理"的数
- 第二次：标准号只要求行首匹配，误伤了 8561 行正文
- 第三次：优先级错了，被前一个规则抢占

**支撑数据**：全库 103 文件实测，从"误切 344 块"到"零误伤"，  
最终陷阱题 recall 翻倍（0.167 → 0.333）。

**关键收获**：验证方式必须匹配真实输入粒度。我最初拿旧索引的  
306 字小chunk 预演，而真实构建是整篇文档进函数，  
切点量级完全不同 —— 这是判据反复改错的直接原因。

## Q6：为什么 faithfulness 一直这么高？

**核心答案**：因为 prompt 强制来源标注，禁止跨片段合并改写。

**具体约束**：

1. 每条结论标 `[片段N]` —— 把陈述与来源显式绑定
2. **禁止跨片段合并改写** —— 模型把多个片段平均融合后就分不清  
   哪句话来自哪一段了，这是幻觉的主要来源
3. 数字原文照抄，不改写

**证据**：优化前某条 faithfulness 只有 0.75（904 字把 4 个片段揉成一段，  
夹了片段里没有的概括表述）。加约束后长期保持 0.985+。

**一个反直觉的补充**：我降低了 23 条弃答（让模型基于现有片段作答），  
**faithfulness 一条没掉**（0.985 → 0.985）。  
我原本假设"答得多会编"，实测不成立。

## Q7：跨文档综合类 recall 只有 0.512，怎么解决？

**诚实回答**：这是我目前明确的瓶颈，还没做。

**我的判断**：这类问题需要查询分解或多跳检索 ——  
"消防技术服务机构出具虚假文件有什么法律责任"需要同时检索  
机构资质规定 + 法律责任条款，而现在的单次检索只能召回其中一个。

**为什么先不动**：在 3 条样本上做的覆盖率公式改动（基数惩罚）  
会让另一条从 5 掉到 6，说明我对这类问题的评分函数还没理解透。  
上 reranker 之前，我想先把分块边界和查询意图的判据做扎实。

**追问：那你的下一步计划是什么？**

1. 先给这类问题单独设计一个评测子集（现在只有 21 条，样本太少）
2. 分析失败案例里答案是否在 top-50 候选池内 —— 如果在，问题是精排；  
   如果不在，问题是召回，需要查询分解
3. 根据结论决定是加 reranker 还是加多跳

## Q8：项目怎么部署？有什么生产化考虑？

**核心答案**：

| 关注点  | 实现                                           |
| ---- | -------------------------------------------- |
| 鉴权   | JWT（HS256）/ OIDC（RS256 + JWKS），支持服务间共享 Token |
| 限流降级 | 三态熔断 CLOSED / OPEN / HALF_OPEN               |
| 成本控制 | Token 与金额双预算闸门，超限降级                          |
| 可观测  | 全链路追踪，OpenTelemetry 兼容                       |
| 任务状态 | Redis 支撑异步任务                                 |
| 失败路径 | 路由最大跳数 3，超限转人工                               |

**关键设计**：**AI 系统的失败路径必须显式设计。**  
不能让它无限重试 —— 所以有转人工、有预算闸门、有熔断。

**举例**：LLM 单点故障导致整个链路停摆后，我加了 provider 主备链  
（DeepSeek 失败自动切通义千问），13 个业务文件零改动。

**追问：故障转移怎么保证可观测？**  
这是我踩过坑才重视的。第一版切换逻辑是对的，但日志只打  
"第 1 次失败，1s 后重试"，看不出到底切没切 —— 用户无法判断它有没有生效。  
后来加了三条：切换时明确打日志、评测报告记录当轮 provider 链、  
统计因故障未生成答案的条数并警告"本轮不可与其他轮对比"。

## Q9：怎么保证分块策略改了以后真的生效？

**核心答案**：不信分数，直接查落库的元数据。

**真实事故**：连续两轮改了分块策略，评测分数**纹丝不动**。  
排查半天发现是重建命令参数写错，**索引从未重建** ——  
检索跑的还是几个月前的 chunk。

**修复**：

1. `build_index.py` 启动时检查索引元数据是否含新分块标记
2. 重建完成后**直接报告实际数量**：
   ```
   分块标记：is_catalog=268  is_tier_table=9
   ```

**延伸**：这个习惯让我在 P4 上又抓到一次 —— `is_tier_table=79` 但  
`is_catalog=0`，说明新版代码生效了但 P4 判据从未命中，  
继续查才发现判据三次都设计错了。

> **"效果完全不变时，先确认代码是否真的执行，再分析策略。"**

## Q10：这个项目你最大的收获是什么？

**三个层次**：

1. **技术上的**：RAG 的瓶颈往往不在算法，而在**数据表示**。  
   我花的时间最多的不是调权重，而是恢复 PDF 丢失的视觉结构。
2. **方法上的**：**先建尺子，再动手术。** 没有分层统计和逐条核对，  
   我会把"加大目录降权"当成正确方向一路调下去 —— 事实上那会  
   把我自己的答案删掉。
3. **认知上的**：学会**主动推翻自己的假设**，也学会**停止调参**。  
   我调了 5 版弃答检测器还在震荡时选择换思路，  
   而不是写第 6 条规则。我也在 3 条样本调出 1 分提升时选择放弃。

## 可能被问到但我需要坦白的

**Q：为什么不用 Milvus / 用了 FAISS 是因为不熟悉分布式吗？**  
两者都实现了。默认 FAISS 是因为开发和评测方便（本地文件、无外部依赖），  
数据量大时 `--backend milvus` 就能切。选型依据是场景需求而非技术偏好。

**Q：评估集只有 47 条，是不是太小了？**  
是，置信区间偏宽。这也是我为什么在 3 条样本上调出的改进会主动放弃。  
扩充到 100+ 条是我明确的 TODO。

**Q：有没有考虑过用 LLM rerank？**  
考虑过。但规则精排的每条规则可解释、可定位，而 LLM rerank 会引入  
额外延迟和不确定性。当前阶段优先修分块边界。

**Q：代码是自己写的吗？**  
框架层（LangGraph 编排、FAISS 集成）是标准用法。  
分块策略（法条感知分块、档位表重组、目录条目切分）、  
检索层（IDF 加权覆盖率、条款匹配分级、查询意图豁免）、  
以及全部评测代码是自己实现的，这部分是主要工作量。
