# 端到端演示 Demo

> 面试现场可当场跑：**`bash agent1/demo/run_demo.sh` → http://127.0.0.1:8800**
>
> 设计原则：**页面上每个数字都是服务端实跑的，没有 mock、没有兜底假数据。**
> 宁可显示"检索失败"，也不显示一个编出来的漂亮结果。

---

## 一、为什么做这个

前四周做完的东西如果只写在文档里，面试官看不到。
而"能跑"和"跑得对"是两个完全不同的问题 —— 演示页的作用是把后者摊开给人看。

它刻意**不展示**这些（对面试没价值）：
- 炫技的动画、渐变、粒子效果
- "我的项目有 20 个功能" 的功能清单墙
- 已经精心调过的顺利案例

它**重点展示**这些（真实交付里会遇到的问题）：
- **检索过程**：命中了哪些片段、怎么排的序、各阶段多慢
- **弃答机制**：查不到时它会不会硬答
- **引用可溯源**：它引用的条款号，是真在检索结果里，还是编的

---

## 二、实测发现：模型会编造条款号

这是做这个演示页时最重要的发现，也是最初没预料到的。

拿 4 个问题跑下来，统计答案里引用的条款号能否在检索片段里找到：

| 问题 | 引用数 | 可溯源 | 编造 |
|------|--------|--------|------|
| 建筑消防设施包括哪些 | 1 | 0 | **1** |
| 公众聚集场所投入使用需要什么手续 | 1 | 1 | 0 |
| 消防设施维护保养要求是什么 | 2 | 0 | **2** |
| 消防救援机构有哪些职责 | 3 | 0 | **3** |
| 消防安全重点单位有哪些消防安全义务？ | 2 | 0 | **2** |

**可溯源率仅 20%。**

具体看最严重的一条：

```
问：  消防救援机构有哪些职责
答：  ...第四条 / 第四十五条 / 第五十三条...

检索实际返回的片段里只有：
      第十五条 / 第六十条 / 第六十二条 / 第六十四条 / 第四十七条
```

**四个条款号，三个是编的。**

而且同一问题跑两次结果还不同 —— 说明这不是稳定能力，是随机波动。

### 为什么这个发现比"准确率 100%"更有价值

消防执法文书有法律效力。编造的条款号会直接影响法律适用，
轻则文书被退回去，重则执法依据站不住。

所以这个项目的态度是：**不回避，而是把它讲清楚，并说明配套机制。**

现场可以这么讲：

> 你看这个查询，它给了答案、给了条款引用。
> 但我做了溯源核对 —— 三个引用里没有一个能在检索结果里找到，
> 是模型编的。这个问题如果糊弄过去，上线后就是错引法条。
>
> 所以我配了三道防线：prompt 层显式约束、审核层用 MCP 工具把
> 涉及法条的改动自动标为高风险、归档前强制人工确认。
>
> 而溯源检测就是第一道防线的验证手段 —— 没有它，
> 你根本知道模型在编。

**这段话比"我的系统引用准确率 100%"有说服力得多。**
后者一追问"你怎么测的"就塌了，前者展示的是判断力。

## 三、页面上有什么

### 1. 检索链路（可展开每一阶段）

| 阶段 | 展示内容 |
|------|---------|
| 查询改写 | 短查询自动补法规前缀（< 15 字） |
| 混合检索 | BM25 + 向量 + RRF 耗时、命中条数 |
| 精排结果 | 每条片段的得分、来源、字数、含哪些条款 |
| 生成 | LLM 耗时、输出字数 |
| 弃答判定 | 命中弃答文案 / 正常作答 + 抽出几处引用 |

耗时实测（4019 片段库，CPU 推理）：

| | 冷启动 | 预热后 |
|---|--------|--------|
| 检索 | 6.5 s | **0.9 ~ 1.2 s** |
| 生成 | — | 1.3 ~ 2.7 s |
| 端到端 | — | 2.8 ~ 4.3 s |

**"首包 6.5s、稳定后 1s 内"是冷启动的典型特征。**
`run_demo.sh` 会在启动时后台预热（实测 6.5~7.4 秒），
避免演示时对着空白页干等。

顺带这是个可讲的点：很多项目是 demo 时预热、上线后忘了，
首包延迟问题要到生产才暴露。

### 2. 生成结果与弃答判定

弃答是**三态**的，这点很重要：

| 状态 | 含义 | 页面显示 |
|------|------|---------|
| 弃答 | 答案含"未检索到相关内容"等文案 | 黄色徽标 + 命中的文案 |
| 正常 | 有实质内容 | 绿色徽标 |
| **不确定** | 既无弃答文案、也短得不像正常答案 | 灰色徽标 |

**为什么要有"不确定"这一态：**

第一版只有 True/False，判定函数写成"没识别到弃答文案就返回 False"。
结果把「"未检索到相关内容。"」判成了"正常作答"——
演示页上出现"明明没答却说没弃答"，比不做演示更糟。

改成三态之后逻辑才对：**识别不到就说不知道**，
因为把猜测说成事实比承认不知道更糟。

### 3. 引用溯源（三态）

| 标记 | 含义 |
|------|------|
| ✓ 可溯源 | 该条款号在某个检索片段里原样出现 |
| ≈ 表述有差异 | 数字一致但措辞不同（如"第十五条" vs "第十五条之一"） |
| ✗ 编造 | 检索片段里根本没这个条款号 |

判定方式是把中文数字转成整数再比对
（"第六十条" → 60），避免表述差异造成误判。

## 四、怎么用

```bash
# 启动（会自动预热，等到"预热完成"再打开页面）
bash agent1/demo/run_demo.sh

# 换端口
bash agent1/demo/run_demo.sh 8801
```

命令行自检（不依赖服务）：

```bash
python agent1/demo/trace_pipeline.py
```

端到端验收：

```bash
python agent1/demo/verify_demo.py
```

验收覆盖 6 类：
1. 页面能加载且关键元素齐全
2. API 阶段数据完整
3. 溯源三态字段齐全、`fragment_count` 与实际片段数一致
4. **前端读取的字段后端都提供**（反向检查，最容易漏）
5. 弃答路径返回结构化错误
6. 引用可溯源率汇总

## 五、验收脚本抓到的两个问题

### 1. 假报警：检查脚本自身的正则作用域错了

「阶段字段齐全」报缺失 `['n', 'q']`，但前端明明能正常渲染。

根因：正则 `\bs\.([a-z_]+)` 全文扫描，把 `SAMPLE` 常量里的
`s.q` / `s.n` 也算进来了 —— 那里的 `s` 来自示例列表，不是 stage 对象。

**两条错误同时出现（说缺 n/q，又说存在 n/q）本身就是"作用域错了"的信号** ——
真缺字段不会反过来多出字段名。

修法：把扫描限定在 `renderStages` 函数体内。

> 与上一轮那个教训同源：**检查脚本报的"字段缺失"要先核对作用域**，
> 直接去改被检查的代码会改坏本来正确的东西。

### 2. 真问题：可溯源性不稳定，没把它改成"通过"

验收报「预期可溯源」但实测 fabricated。

一开始以为是匹配 bug，去查 markdown 格式、简繁体差异，
查完才确认 —— **同一问题两次跑，一次 ok 一次 fabricated**。

处理方式**不是改成通过**，而是改成观测项：

```
[观测] 引用可溯源性：部分可溯源（1/2）
       ↑ LLM 输出不稳定，引用准确性需多次统计，
         不能靠单次演示下结论
```

**验收脚本报假问题就该改脚本；报真问题时改成"通过"是自欺** ——
那等于把风险藏起来。

## 六、文件清单

| 文件 | 作用 |
|------|------|
| `trace_pipeline.py` | 链路追踪核心：检索/生成/弃答/溯源，旁路观测不改链路 |
| `demo_server.py` | FastAPI 服务，`/api/demo/ask` + 静态页 + 启动预热 |
| `index.html` | 单文件前端（无构建步骤，双击即开） |
| `run_demo.sh` | 启动脚本，按端口杀旧进程 + 等预热完成 |
| `verify_demo.py` | 端到端验收，6 类检查 |

**刻意没有的东西**：没有 mock 层、没有假数据兜底、
没有 `requirements_demo.txt`（复用主 requirements）。

理由见 `trace_pipeline.py` 开头的注释 ——
演示的价值恰恰在于"这些数字是真的"。
