## 一、整体架构与数据流

### 1.1 拓扑

四个 Python 服务 + 基础设施层：

```
                        ┌─────────────────────┐
   客户端 ──JWT──▶  gateway:8000          │  级联路由 + 熔断降级 + 异步任务
                        └──────┬──────────────┘
             ┌─────────────────┼─────────────────┐
             ▼                 ▼                 ▼
      agent1:8001         agent2:8002        agent3:8003
      法规RAG+文书          语音(ASR/LLM/TTS)   视觉(OCR/YOLO/VLM)
             └─────────────────┼─────────────────┘
                               ▼
        ┌──────────────────────────────────────┐
        │ Redis(异步任务/缓存) · Milvus(向量)  │
        │ etcd+MinIO(Milvus依赖)               │
        │ Prometheus+Grafana(监控)             │
        │ OTel+Langfuse(链路追踪)              │
        └──────────────────────────────────────┘
```

服务依赖与健康检查（`deploy/docker/docker-compose.yml`）：

| 服务 | 端口 | depends_on | 存活探针 | 就绪探针 |
|---|---|---|---|---|
| gateway | 8000 | redis + agent1/2/3 全部 `service_healthy` | Dockerfile `/` | — |
| agent1 | 8001 | redis | `/health` | `/ready`（查索引+模板+目录可写）|
| agent2 | 8002 | agent1 | `/health` | `/ready`（查 ffmpeg）|
| agent3 | 8003 | 无 | `/health` | `/ready`（查 YOLO 权重+ffmpeg）|

**探针分离是刻意设计**（`agent1/server.py:124-143`）：

> 存活探针：只回答「进程还在不在」。刻意不查任何外部依赖。Dockerfile 的 HEALTHCHECK 打这个端点，如果这里去连 Redis/Milvus，那么外部依赖一抖容器就被判定 unhealthy、被编排器重启—— 但进程本身没有任何问题，重启也修不好。
> 就绪探针：回答「现在能不能接流量」。与 /health 分开，是因为这两件事的处置方式完全不同：/health 失败要重启，/ready 失败只需要摘流量。

### 1.2 四条请求路径

| 路径 | 端点 | 编排方式 | 适用 |
|---|---|---|---|
| A 同步 | `POST /dispatch` | `route()` → 单 agent | 纯文本问答，最常用 |
| B 文件 | `POST /dispatch_file` | 后缀覆盖路由 → 单 agent | 上传单文件（只支持 vision/voice）|
| C 异步 | `POST /dispatch_async` | 后台 task + Redis + SSE | 长耗时任务 |
| D 多模态编排 | `POST /dispatch_multimodal` | **LangGraph 状态图** | 视频+语音+文书混合场景 |

### 1.3 路径 A 的完整数据流（以法规问答为例）

```
1.  POST /dispatch {query, file_path?, force_kind?, conversation_id?}
2.  get_current_user 校验 JWT → UserCtx(sub, dept, role, clearance)
    ├ HS256 本地签名（jwt_secret 强制 ≥32 字节，RFC 7518 §3.2）
    └ OIDC RS256（配 jwks_url 时走，额外校验 iss/aud）
3.  AuditMiddleware 捕获请求/响应摘要，脱敏后写 logs/audit.jsonl
4.  DRY_RUN=1 → 直接返回路由信封，不转发
5.  route(query, file_path)  三级级联 → RouteDecision
6.  kind = force_kind or decision.kind
7.  protected_call(handle_rag, ...)  熔断 + 2 次指数退避 + 降级兜底
8.  httpx POST agent1/api/rag/ask {question, top_k:8} + X-Internal-Token
9.  rag_ask → hybrid.search(query, k) → DeepSeek(deepseek-chat, temp=0.1)
10. 返回 {"status":"success", "routed_to", "route":envelope, "result"}
```

### 1.4 路由：三级级联（`common/router.py:209-262`）

```
L1 规则（文件后缀 → 关键词）      置信度 1.0 / 0.7~0.9
  ↓ 未命中
L2 本地分类器（Tfidf + LogisticRegression）  阈值 0.6
  ↓ 未命中 / 模型不存在
L3 LLM 兜底（deepseek-chat, temp=0, 10s, max_tokens=50）  阈值 0.5
  ↓ 全不中
默认 rag（source="default"）
```

**L1 的判据顺序有讲究**（`common/router.py:68-98`）：文件后缀优先，置信度直接给 1.0 —— 后缀是最强信号，关键词只是次级。

关键词置信度公式 `min(0.9, 0.6 + 0.1 * score)`：命中 1 个词 = 0.7，2 个 = 0.8，3 个封顶 0.9。

**L3 的 JSON 提取很宽容**（`common/router.py:145-154`）：容忍 ```` ```json ```` 围栏与前后废话，取首个 `{` 到末个 `}`。

**每级都有独立的降级路径**：L2 模型文件不存在 → 返回 None 落到 L3；L3 的 key 为空/超时/JSON 解析失败 → 返回 None 落默认。**任何一级失败都不抛异常**。

### 1.5 LangGraph 编排（`orchestrator_langgraph.py`）

**State 定义**（`:61-77`）含 16 个字段，其中 `errors` 用 `Annotated[list[str], operator.add]` —— 多个节点并行报错时能累加而不互相覆盖。

**9 个节点 / 3 个条件边**：

```
START → classify ─┬─ vision ────┐
                  ├─ voice ─────┤→ synthesize ─┬─ extract_fields → doc_draft ─┬─ review_submit → report → END
                  ├─ doc_extract ┤              └─ report (降级)
                  └─ synthesize (无文件)
```

- `route_after_classify` 返回**列表**（LangGraph fan-out，三个模态节点并行）
- `route_after_synthesize` 查模板格式 + 预算
- `route_after_doc_draft` 查 review_id 是否生成

**预算双检**（`:337`、`:371`、`:428`）：节点入口 + 条件边各查一次 `budget.check()`，超限则降级到 report 并在 errors 里记明原因。

**checkpointer**：`SqliteSaver` 存 `logs/checkpoints.sqlite`，按 `thread_id` 分区。

## 二、五大技术难点与设计取舍

### 难点一：检索质量归因 —— 先分清是 LLM 的问题还是检索的问题

**这是整个项目最核心的一条方法论。**

改造前的实测数据把问题切得很干净（`agent1/hybrid.py:4-15`）：

> ```
> 改造前：faithfulness=0.986 / answer_relevancy=0.88（LLM 层没问题）
>         context_precision=0.165 / context_recall=0.60（检索层崩了）
> ```

faithfulness 0.986 说明模型**不会编造**；precision 0.165 说明检索**塞了 5 段里只有 1 段相关**。这两种问题的解法完全不同 —— 前者要改 prompt，后者要改分块和排序。**归因错了，后面所有优化都是白做。**

定位到检索层后，逐层排查找出三个根因（`agent1/hybrid.py:7-15`）：

> ```
> 1. `_precise_search` 三处 `return xxx[:k]` 完全无相关性排序，
>    按 docstore 物理顺序截断 —— 相当于随机返回。
> 2. 精准路径命中后直接 return，跳过混合检索与 RRF，
>    误召回无法被语义信号纠正。
> 3. dedup key 用 `page_content[:80]`：法条引用重叠（"依照本法第X条"）
>    会让多个 chunk 前 80 字符相同 → 误合并，把正确 chunk 挤掉。
> ```

#### 取舍 A：精准命中**只作强先验，不短路**

改动（`agent1/hybrid.py:611-612`）：

```python
# ★ 1) 精准定位 —— 只作为强先验，不短路
precise = self._precise_search(law_kw, article, k, query=query) or []
```

**理由**：短路 = 让单一信号（条款号匹配）独占决策权 = 误召回无法被语义信号纠正。改成「精准结果不决定结果，只作为一路加权信号参与融合」。

**但先验的量级必须绝对**（`agent1/hybrid.py:637-647`）：

> ```
> 关键：RRF 自身的量级是 1/(60+rank) ≈ 0.016 ~ 0.008，
> 两条向量+BM25 双命中也就 0.03 左右。而精准分数是 12~15 量级。
> 若按比例归一化再乘系数（旧的 0.02 * ratio），boost 只有 0.02，
> **与 RRF 原分同量级，起不到任何排序作用** —— 这正是"精准命中
> 仍然被噪声挤掉"的直接原因。
> ```

#### 取舍 B：条款匹配分级，低级别命中是**噪声源**而非弱证据

分级定义（`agent1/chunking.py:421-428`）：`3=到项 / 2=到款 / 1=到条 / 0=不匹配`。

**分级是失败案例驱动的，不是理论设计**（`agent1/chunking.py:311-323`）：

> ```
> # 为什么要分级（由真实召回失败案例驱动，非理论设计）：
> # 评估问题"《消防法》第六十条第一款第七项规定了什么？"在 top_k=5 下
> # precision=0 / recall=0，召回的5 条分别是"第六十条第一款第一项""第四十七条"
> # "第六十条第一款第二项"…… 全是"第六十条的邻居"，唯独缺第七项本身。
> ...
> # 另一个反直觉点：法条原文的项写作"（七）"而不是"第7项"，所以纯字面匹配
> # 对**真正的答案**返回 False，对噪声片段返回 True —— 区分度完全反了。
> ```

因此过滤逻辑是**宁缺毋滥**（`agent1/hybrid.py:381-389`）：

```python
best = max((lv for lv, _ in levels), default=0)
if best < 2:
    logger.info("条款 '%s' 最高仅匹配到 lv=%d，不走精准强先验", article, best)
    return None
```

lv=1（只对到"条"）不是"弱证据"，它**正是把答案挤掉的"第六十条的邻居"** —— 所以宁可完全放弃这一路先验。权重差距也据此拉开（`agent1/hybrid.py:177-182`）：`W_MATCH = {3: 12.0, 2: 8.0, 1: 4.0, 0: 0.0}`。

#### 取舍 C：法名识别以索引 metadata 为权威，不靠词典

（`agent1/hybrid.py:56-67`）

> ```
> 实测修复（来自 RAGAS 逐样本诊断）：
>   "公众聚集场所投入使用营业前消防安全检查实行什么制度？" -> 法律名=None
> 问题不在"词典没收录"，而在**索引里的law 字段才是权威**：
>   而短名"消防法"会同时匹配 4 个文件，候选被污染。
> 方案：**词典只做粗筛，最终以索引 metadata.law/doc_id 精确锁定。**
> ```

同时保留正文兜底召回（`agent1/hybrid.py:103-112`）—— 某些主题词只出现在正文里，`《高层民用建筑消防安全管理规定》` 根本不在知识库里，只有其他文件在正文中引用它。

#### 取舍 D：tier 只作**弱先验**，不压过词面相关性

（`agent1/hybrid.py:316-326`）

> ```
> 排序：**词面相关性主导，tier 只作弱先验**。
> 早期版本让 tier 绝对优先，实测把正确 chunk 压到 rank 6~10
> （查询"消防行政处罚的裁量基准是什么"时，权威 law 名命中的
> 裁量基准表格排在"第二条 裁量定义"之前）。但 tier 只是"这个文件
> 名义上相关"的弱证据，真正决定相关性的是 chunk 本身讲不讲这个问题。
> ```

对应常量 `_TIER_WEIGHT = 0.3`（`agent1/hybrid.py:122-124`）：「刻意小于 1：够用来在同一 cover 分数下破同分，不够压过内容本身」。

### 难点二：PDF 视觉结构丢失 —— 必须在入库前恢复边界

**根因**（`agent1/chunking.py:2-25`）：

> ```
> 1. **PDF 噪声**：--- 第 14 页 ---、页脚页码、\x14\x00 0 0 3 2 \x14
>    （PDF 内部标记符）等被原样切进 chunk，向量与 BM25 都被污染。
> 2. **法条被拦腰截断**：法条是"第X条"为单位的**语义原子**。
>    通用 RecursiveCharacterTextSplitter 按 500 字硬切，
>    第六十条第一款可能被切到两个 chunk 里，任一片段都不完整。
> 3. **元数据缺失**：只有 source/doc_id，检索时无法按"法律名+条款号"
>    做结构化过滤，只能靠向量硬碰。
> ```

#### 取舍 A：两套目录判据，因为两份真实目录文档的边界信号完全不同

（`agent1/chunking.py:641-666`）

> ```
> # 实测两份真实目录文档，边界信号完全不同，因此需要两套判据：
> #   A. 序号型——《关于优化强制性产品认证目录的公告（2020年第18号）》
> #      4056 个非空行里：中文序数+类目名+计数 16 处；数字.名词(4位编码) 19 处
> #   B. 标准号锚型——《消防产品目录（2022年修订本）》
> #      2264 个非空行里，序号型切点 **0 处**，通篇是三行拍平的
> #      "产品名+说明 / 说明续行 / GB 标准号"
> #      唯一稳定信号是**标准号独占整行**。注意必须是"独占"：
> #      导则类正文中标准号是句内引用，行首匹配会把整篇切碎。
> ```

阈值来自全库 103 个文件实测（`agent1/chunking.py:667-677`）：

| 文件 | 非空行 | 独占标准号行 | 占比 |
|---|---|---|---|
| 关于优化强制性产品认证目录的公告 | 4056 | 365 | **9.00%** |
| （应急消〔2022〕136号）消防产品目录2022 | 2264 | 127 | 5.61% |
| 浙江省建筑工程消防验收操作技术导则 | 8561 | 13 | **0.15%** |
| 其余 99 个文件 | — | 0 | ~0 |

> 导则的 0.15% 与目录的 5.61% 差 **37 倍**，阈值取 2% 留足安全边际。

**这个「37 倍」是分块阈值不按通用经验取、而按自家语料实测分布定的直接依据。**

#### 取舍 B：不用「中位间隔」判定 —— 因为没看真实数据

（`agent1/chunking.py:744-747`）

> ```
> 启用条件：切点数 >= ``_CATALOG_MIN_CUTS``。
> **不再用中位间隔判定**：实测该文档 35 个切点的中位间隔是 95 行
> （每个大类下有一整张几十行的产品表），任何"间隔要小"的阈值都会
> 把它误判为非目录——这正是之前 `is_catalog=0` 的直接原因。
> ```

`docs/rag-tuning-journey.md:179-189` 把这条归类为：**「这是"没有看真实数据就定阈值"的典型后果。」**

#### 取舍 C：P1 裁量表按「档位行」重组，P4 目录按「条目」切分

**P1 裁量基准表格**（`agent1/chunking.py:479-503`）：

> ```
> # precision 低的头号噪声源（实测：RAGAS 报告里的多数噪声 chunk 属此类）。
> # 成因：裁量基准附件是**三列表格**，PDF 抽出来是这样：
> # 法条边界切分在这里完全失效（表格行没有"第X条"），
> # 500 字硬切的结果是一块里塞了 3~5 个互不相干的违法行为主题
> # 解法：按「档位行（严重/一般/较轻）」切分组，每组 = 一个违法行为
> # + 它的全部档位，这才是一个语义原子。
> ```

**P4 目录条目**（`agent1/chunking.py:613-639`）：

> ```
> 即：用户要的是"电线电缆"这一个条目，而它被夹在"总体说明"和"下一个条目"
> 之间，**没有任何结构性标记告诉检索系统"到这里是一个条目的结束"**。
> Bag-of-words 对齐失效 —— 命中"电线电缆"的 chunk 混了另外两个主题，
> 命中"产品/目录"的 chunk 又不含答案，无论怎么调权重都排不准。
> 这和 P1（裁量基准表格）本质相同：**PDF 的视觉结构在纯文本里丢失了，
> 必须在入库前把它恢复出来**，否则检索层再聪明也无从判断边界。
> ```

#### 取舍 D：P4 必须排在 P1 之前判

（`agent1/chunking.py:978-984`）

> ```
> **P4 必须排在 P1 之前**：实测《关于优化强制性产品认证目录的公告》
> 里每个产品条目都是"若干行说明 + 一个处罚档位"的排版，
> ``regroup_tier_table`` 会把它整篇判成档位表（45 块全部标成
> tier_table），于是电线电缆这类**目录条目被当成档位组**，
> 既丢了 ``is_catalog`` 标记，又让 P2 降权判据用错。
> 目录特征（大量"数字.名词(4位编码)"切点、独占标准号密度）比
> 档位特征更结构化、更难偶然命中，所以先判目录。
> ```

#### 取舍 E：宁可前言粘在首条目上，也不让条目边界丢失

（`agent1/chunking.py:779-783`）

> ```
> 早期实现把"第一个标准号之前的全部行"当作前言单独成块，结果
> 第一个产品条目的说明行被卷进前言块，条目失去自己的标准号。
> PDF 纯文本里无法可靠区分前言与首条目描述，因此不剥离——
> **宁可前言粘在首条目上，也不让条目边界丢失。**
> ```

### 难点三：测量方法本身会骗人 —— 评测体系的三道防线

这是本项目**最能体现工程判断力**的部分，也是面试里最能讲深的部分。

#### 防线一：上下文指纹 —— 识别空跑

**痛点**（`agent1/eval/local_eval.py:356-368`）：

> ```
> ★ 这套机制的全部理由（2026-10-15 实测踩坑）：
>   v6/v7/v8 三轮跑完，总分"有涨有跌"，很自然会解读成调优时灵时不灵。
>   但逐条比对 contexts 发现三轮 47 条上下文**逐字完全相同**——
>   索引没动过，v8 是次空跑。
> ```

**指纹的构造有一条硬规则**（`agent1/eval/local_eval.py:388-397`）：

> ```
> """上下文指纹：只哈希 question + contexts。
> ★ 绝不能包含答案与分数。
>   含了的话分数一变指纹就变，空跑检测立刻失效——
>   而空跑检测是这三项机制里最有用的一项。
> 实测：v7/v8/v9 三份报告指纹完全相同（cb941a0116de7cef），正是空跑的铁证。
> """
```

**空跑的判据是「指纹一致 AND 分数有变」**（`agent1/eval/local_eval.py:577-588`）：

> ```
> ★ 语义澄清（这里我一度改错，值得记下来）：
>   空跑的判据是「指纹一致 **且** 分数有任何变化」，
>   **不是**「指纹一致且变化超出噪声底」。
>   为什么不用噪声底当条件：指纹一致已经意味着检索层零变化，
>   此时分数的任何变化都不可能来自策略改进 —— 只能是 LLM 抖动。
>   而且指纹一致 + prec 0.221→0.222 也该报空跑：
>   它说明"什么都没改却动了分数"，这本身就是需要知道的事实。
> ```

**处置是「阻断」不是「警告」**（`docs/eval-trust.md:78-82`）：

> `compare_with_baseline()` 在这种情况下返回退出码 1，`local_eval.py` 直接 `sys.exit(1)` —— **不是打个警告，是阻断**。理由：错误的结论一旦被写进文档，就会被当成面试素材带出去。

#### 防线二：噪声底 —— 差异小于它就没有结论

**为什么阈值是 0.10 而不是实测的 0.021**（`agent1/eval/local_eval.py:373-385`）：

> ```
> ★ 为什么必须是 0.10 而不是实测的 0.021：
>   实测抖动是在特定数据集 + 特定 judge 上测的，换数据集就不一定成立。
>   更重要的是：**单次 A/B 差值只是抖动幅度的下界，不是幅度本身。**
>   曾拿 v7/v8 的差值（recall 0.021）当阈值设成 0.02，
>   结果 v7→v8 的 recall 差值恰好 0.021，卡在边界上，
>   `abs(0.021) > 0.02` 判真，测试直接失败。
>   差值分布有方差，两次恰好接近不代表常态如此。
>   tests 里有一条专门锁定这个决策：若有人调回 0.02，
>   必须先解释为什么单次观测可以当阈值用。
> ```

#### 防线三：不可比时不给 verdict

（`agent1/eval/local_eval.py:507-508`）

```python
if note:
    return out          # 不可比时不给 verdict——比什么都不报更危险
```

配套的还有一条读错位置的警告（`agent1/eval/local_eval.py:421-428`）：

> ★ 报告的真实结构：
>     scores.<metric>       均值在这里

### 难点四：精度优化的三次 A/B —— 包括一次「做了但回退」

#### 案例 A：idf² 超线性加成 —— 做了，回退了

（`agent1/hybrid.py:507-529`）

> ```
> # ★ 这里试过 idf² 超线性加成，三轮 A/B 后回退（见 docs/rerank-ab-log.md）：
> #   动机：原来的 `if t in text` 是 bool 命中，
> #   命中 1 次和 5 次同权 → 10~32 个候选并列满分，
> #   BM25 把 P4 标准条目排第 1 的判断被抹平。
> #   实测后果（47 条）：
> #       直查法条     n=20   recall +0.050   ← 单文档精确查找，确实受益
> #       跨文档综合    n=21   recall -0.143   ← 答案横跨多份文件受损
> #       陷阱题       n= 6   recall -0.167
> #   原因：跨文档类答案分布在多份文件里，
> #   **每个片段都只命中 1 个查询词**，
> #   而单词命中在 idf² 下权重极高，压过了命中 2-3 词的片段。
> #   idf² 优化的是"找准那一条"，代价是"找齐那几条"——
> #   跨文档类占样本 45%，代价超过收益。
> #   保留 bool→线性加权这一段的原因：
> #   IDF 加权本身是对的（答案词"电线电缆"df=12 vs
> #   噪声词"消防"df≈2000，本就该有区别）。
> #   错的是"超线性"这个选择，不是"加权"本身。
> ```

**但保留了一个结构性收获**（`agent1/hybrid.py:229-240`）：

> ```
> #   **保留拆分的意义**：BM25 与精排不再共用 idf 上限，
> #   今后调精排不会连带影响召回 —— 这是本轮最重要的结构性收获。
> _IDF_MAX_BM25 = 3.0
> _IDF_MAX_RERANK = 3.0
> ```

#### 案例 B：改一个常量 ≠ 改一个变量

（`agent1/hybrid.py:211-227`）

> ```
> # ★ IDF 上限拆成两个，因为 BM25 与精排共用同一份 idf 字典。
> #   原先只有 _IDF_MAX 一个，改它会**同时**改动
> #     - BM25 召回打分（__init__ 里构建 self._idf）
> #     - 精排覆盖率（_rerank 里 weights 直接读 self._idf）
> #   实测教训（47 条 A/B）：改 _IDF_MAX 3.0->8.0 后
> #     top5 完全相同   8/47  (17%)
> #     集合大变       13/47  (28%)
> #   也就是说**召回阶段早就变了**，而我当时以为自己"只改了精排"。
> #   于是把时间花在了精排覆盖率上（改 B 方案），
> #   结果分层数字逐位不变 —— 瓶颈根本不在那里。
> #   教训：**「改一个常量」不等于「改一个变量」。**
> #   共享的可配置项是调参时最大的陷阱，必须先确认它的作用域。
> ```

#### 案例 C：IDF 上限把加权效果自己抹平了

（`agent1/hybrid.py:190-209`）—— 这是「参数定位」的经典案例：

> ```
> # ★ _IDF_MAX 从 3.0 提到 8.0，这是一个定位出来的实质修复。
> #   实测（N=4019）查「电线电缆类产品属于消防产品吗」的 5 个查询词：
> # 词          df     raw_idf   截断后(MAX=3)  截断后(MAX=8)
> # 电线电缆    12      5.734        3.000          5.734
> # 属于        123     3.479        3.000          3.479
> #   上限是 3.0 时，**df<200 的词全部压成同一个值**——
> #   真正的答案词「电线电缆」(df=12) 和纯噪声词「属于」(df=123)
> #   权重完全相同，IDF 加权等于没加。
> #   这解释了为什么加了 IDF 加权之后 precision 依然上不去：
> #   问题不在加权公式，在参数把加权效果自己抹平了。
> ```

#### 案例 D：降权 vs 过滤 —— 检索侧的取舍

（`agent1/hybrid.py:397-408`）

> ```
> # 为什么是"降权"而不是"过滤"：
> #   裁量基准表格恰恰是问"怎么处罚"时的正确答案，标准名录里的
> #   GB/T 号也可能是问题主体（如"依据哪个规范验收"）。一刀切删除会
> #   直接砸掉 recall（已经 1.0 的指标不能再掉）。所以只压排序权重，
> #   让强信号（条款精确命中）依然能把它们捞回top-k。
> # 幅度刻意小于 W_MATCH[2]=8.0，也小于 W_OVERLAP 满档 1.5：
> # 只压得动"语义相近但没答到点上"的噪声，压不动真答案。
> ```

**但降权判据只看 chunk 自身不够**（`agent1/chunking.py:1067-1075`）：

> ```
> # 这是 47 条评测打出来的补丁：4/6 陷阱题 recall=0，根因全部是 P2 把
> # 《消防产品目录》的 chunk 降权挤出 top-k —— 而用户问的恰恰是
> # "消防产品目录涵盖哪些大类"，这些 chunk 里就写着"一、电线电缆（3 种）"。
> # 教训：**降权判据只看 chunk 自身不够，必须叠一层查询意图。**
> # 同一个 chunk 对"电动自行车怎么处罚"是噪声，对"产品目录有哪些"是唯一答案。
> ```

豁免的**位置**也有讲究（`agent1/chunking.py:1107-1110`）：放在标题/义务性两道闸门**之后**，否则标题不含"目录"的内容也会被误豁免，范围过宽。

### 难点五：执法场景的可靠性要求 —— 静默失败比崩溃更危险

#### 取舍 A：LLM 降级分三级，最后一级是「保留原文」

（`common/llm_guard.py:15-28`）

> ```
> ★★★ 落地场景（本项目最关键的一条）★★★
> 消防执法场景中，如果云端 LLM（DeepSeek）不可达 —— 网络不通、限流、
> 密钥失效 —— 当前实现会让整个请求 500 掉。
> 执法员填了一半的执法文书就丢了，这在生产环境是不可接受的。
> 所以降级策略不是「返回一句错误提示」就完事，而是**分三级**：
>     1. 优先重试（429/5xx/超时）—— 指数退避，最多 N 次
>     2. 熔断后 → 切本地模型（provider_mode=local/hybrid 时可用）
>     3. 本地也没有 → 抛 LLMUnavailableError，由调用方转 503
>        并**保留已检索到的法条原文**（纯检索结果仍然有价值）
> 第 3 条最关键：**宁可给执法员一份没有 AI 解读的法条原文，
> 也不要给一个编造的答案，也不要让整个请求失败。**
> ```

**401/403 判定为不可重试**（`common/llm_guard.py:59-73`）：

> ```python
> # 明确不可重试的（鉴权失败、参数错误）直接 False —— 重试也没用，
> #   反而会把密钥失效拖成 30 秒超时。
> ```

**超时从 600s 收紧到 30s**（`common/config.py:92-95`）：

> ```
> # 单次请求超时。★ 原来 config.py 里是 600s（client 300s）——
> # 执法场景等 10 分钟不可接受，收紧到 30s。
> ```

#### 取舍 B：索引增量「先删旧块再插新块」，删除失败必须中断

（`agent1/index_state.py:2-46`）

> ```
> 原实现的 `_processed_files.json` 只是一份 fingerprint 的集合：
>     ["013725fd...", "04cd2874...", ...]     # 103 条
> fingerprint = md5(path | mtime | size)，只能回答
> 「这个文件处理过吗 / 变过吗」。它**无法回答**：
>     「这个文件在索引里对应哪些 chunk？」
> 于是增量更新变成**只增不删**：
>     某份法规改了 → fingerprint 变了 → 新块插进索引
>                   → 但**旧块还在** → 检索时新旧两版条文同时返回
>                   → 模型可能引用已作废的条款
> **在消防执法场景这直接导致文书出错。**
> ```

**删除失败必须抛异常**（`agent1/build_index.py:295-299`）：

> ```
> # ★ 删除失败必须中断，不能继续
> # 删不掉旧块 → 新旧两版条文并存 → 检索可能命中已作废的条款 →
> # 模型把它写进处罚决定书。**这是会出执法事故的静默失败**，
> # 所以这里抛异常中断，而不是打条日志继续跑。
> ```

**diff 必须以「路径」为基准而非指纹**（`agent1/index_state.py:148-159`）：

> ```
> ★ 关键：以「文件路径」为基准，而不是指纹
>   指纹 = md5(path | mtime | size)，**文件一改，指纹就变**。
>   所以如果按指纹比对，改版的文件会同时表现为
>   「旧指纹 removed」+「新指纹 added」，
>   而看不出「这是同一个文件的改版」——也就没法在改版时先删掉旧块。
> ```

**两套 ID 的坑**（`agent1/index_prune.py:9-19`）：

> ```
> ★★★ 两套 ID 的坑（实测踩过）
> - Milvus：按 ``metadata.chunk_id``（业务 ID）做 expr 删除
> - FAISS：docstore 的 key 是 **UUID**，``FAISS.delete(ids=...)`` **只认 UUID**，
>   传业务 chunk_id 会直接报 "Some specified ids do not exist"
> 所以状态文件里两套 ID 都要记。
> ```

#### 取舍 C：高危改动「拦截」而非「提示」，且先判断后移动

（`agent1/server.py:454-472`）

> ```
> # ★ 为什么是「拦截」而不是「提示」
> # 原实现检测到高风险后照常批准，只在返回消息里写
> # 「请管理员复核报告」—— 但文书**已经归档成终稿了**。
> # 提示会被忽略，拦截才会生效。
> # ★ 为什么只在有高风险时才拦
> # 正常文书（无高风险改动）不该增加额外摩擦 —— 否则运营会为了省事
> # 习惯性勾选确认，机制就白做了。
> if high_risk > 0 and not confirm:
>     # ★ 这里**一个文件都没动过** —— 拦截发生在移动之前。
>     #   （第一版是「移动 → 拦截 → 回滚」，回滚可能失败导致状态不一致。）

#### 取舍 D：审计写失败默认不上抛 —— 因为「写失败让业务失败」更糟

（`common/audit_reliability.py:19-32`）

> ```
> 1. **写失败不再静默** —— 记到死信队列 + 打 Prometheus 指标 + 严格模式下上抛
> 2. **同步落盘** —— 原来依赖文件缓冲，进程被 kill 时可能丢最后几行
> 3. **可观测** —— `fire_audit_write_failures_total` 指标，失败率 > 0 就该告警
> ★ 为什么默认不上抛
> 「写失败就让业务失败」看起来最严格，但实际会造成
> **审计服务故障拖垮执法业务** —— 磁盘满的时候文书也生成不了了，
> 那才是真正的执法事故。
> 所以默认策略：**业务不中断 + 留死信 + 指标告警**，
> 同时提供 `AUDIT_STRICT=1` 开关给「审计必须保证」的部署场景。
> ```

#### 取舍 E：并发 —— 判断依据是「是否 async」，不是「调用是否阻塞」

（`agent1/server.py:234-238`）

> ```
> # ★ rag_ask 是同步阻塞（内含云端 LLM HTTP 调用，可能 30 秒）。
> #   在 async def 里直接调会卡住整个事件循环 ——
> #   一个请求能把该 worker 的所有其它请求一起堵死。
> #   挪到线程池后事件循环保持自由，并发才真正生效。
> ```

而 `def` 端点是安全的（`agent1/server.py:313-315`）：

> ```
> # 注：本端点是 `def`（非 async），FastAPI 会自动丢到
> # threadpool 执行 —— 这里的同步阻塞调用不会卡住事件循环。
> # （只有 `async def` 端点里的同步调用才是问题。）
> ```

**用 AST 写门禁而不是 grep**（`deploy/tools/check_async_blocking.py:3-11`）：

> ```
> ★ 为什么用 AST 而不是 grep
> grep 会把 `def` 端点（本来就在线程池，没问题）也报出来，
> 也会漏掉多行调用的第二行。用 AST 解析才能准确知道：
> 「这个函数是不是 async」+「它里面调了哪些已知阻塞函数」。
> ```

## 三、关键实现细节

### 3.1 检索链路（五步）

```
① 解析         parse_query → 法律线索 + 条款号（LAW_ALIASES 20 个别名，长别名优先）
② 精准定位     _precise_search → 分级筛掉 lv<2 的候选 → 强先验（不短路）
③ 双路召回     FAISS 向量 (pool=max(k*10,50)) + BM25(jieba 分词) → RRF 融合 (k=60)
④ 先验注入     LV3 +0.30 / LV2 +0.15（绝对量级，非比例归一化）
⑤ 规则精排     条款分级 + IDF 加权覆盖率 + 长度惩罚 + P1/P2 结构降权 → MMR(λ=0.75)
```

**精排权重**（`agent1/hybrid.py:184-188`）：`W_LAW=3.0`（法律名命中）、`W_OVERLAP=1.5`（查询词覆盖率）、`LEN_PENALTY=0.6`（短于 80 字符）、`PENALTY_TIER_TABLE=0.6`（P1 档位表）、`PENALTY_STD_CATALOG=1.2`（P2 引用名录）。

**MMR 的作用**（`agent1/hybrid.py:559-564`）：`lam=0.75`，用 Jaccard 相似度抑制同文档的重复片段。

### 3.2 文书生成链路（三级分流）

```
extract_fields_from_template(docx) → 字段列表
  ↓
split_fields → (普通字段, 法律字段)        rag_legal_advisor.py:53
  ↓
extract_fields_from_case(case_text, fields, case_dict, use_rag_for_legal)
  ├─ FACT    → LLM 从案情抽                        case_field_matcher.py:88-100
  ├─ LEGAL   → 2a 法律依据类：RAG + LLM 归纳        :116-122
  │            2b 处罚决定类：依赖法律依据生成        :124-138
  └─ DERIVED → 规则推导，**完全不调 LLM**          :153-156
  ↓
verify_extraction → LLM 交叉校验（不一致时 corrected 覆盖 + 标「需人工核对」）
  ↓
build_review_table → 状态：已抽取 / 未检索到 / 需人工核对 / 低置信
  ↓
回填：fill_paragraph_placeholders + fill_table_cells → output/*.docx
```

**三级分流的真正价值在 DERIVED 不调 LLM**（`agent1/case_field_matcher.py:153-156`）—— 文号、改正期限、复议机关、执行方式和期限这类**程序性套话**（30+ 条规则）由确定性规则生成，不经 LLM 就没有幻觉风险。

**校验器的修正是「带警告的修正」**（`agent1/case_field_matcher.py:186-197`）：`corrected` 直接覆盖抽取值，但状态同时标为「需人工核对」—— 人工仍能看到原值与修正值。

### 3.3 改动检测与风险分级

**四类风险要素**（`agent1/change_detector.py:61-80`）：金额、条款引用、法律名称（书名号）、关键程序性动词（责令改正/吊销/从重/从轻/立案…）。

**新增 vs 修改差异化定级**（`agent1/change_detector.py:213-215`）：

> ```
> # 纯新增即使含要素也只算中风险 —— 不该把补充说明与越权改罚同等对待
> return ("medium", reasons) if is_insert else ("high", reasons)
> ```

**整段重写也算中风险**（`:217-220`）：`difflib` 相似度 < 30%。

**LLM 只用于高/中风险**（`:496-497`）：纯格式类改动不值得花 token。LLM 归因五分类：抽取错误 / 事实修正 / 格式偏好 / 越权改动 / 其他。

### 3.4 MCP 工具治理

**暴露三组能力**（`mcp/change_detector_server.py:9-21`）：3 个工具（compare_documents / list_reports / get_report）、2 个资源（reports://index、reports://{id}）、1 个 prompt（review_changes）。

**路径安全策略的取舍**（`:32-38`）：

> ```
> MCPServer 默认 ResourceSecurity(reject_absolute_paths=True,
> reject_path_traversal=True, reject_null_bytes=True)。
> 本工具必须读用户给的绝对路径（文书在 /home/... 或 D:/...），
> 所以显式放开 reject_absolute_paths，但**保留**路径穿越与空字节防护 ——
> 前者会让工具在本场景下完全不可用，后两者是真实的安全边界，不能一起关。
> ```

**stdout 被 MCP 协议占用**（`:268-272`）：任何 print 都会污染 JSON-RPC 帧，必须走 stderr —— 这是最常见的 stdio transport 故障原因。

### 3.5 可观测性

**11 个 Prometheus 指标 + 2 个审计指标**（`common/metrics.py`）：请求总数/延迟、检索延迟/片段数、LLM 调用/token/延迟、熔断器状态/切换次数、预算耗尽、MCP 调用、审计写失败/死信积压。

**三条设计原则**（`common/metrics.py:19-27`）：全部可选依赖（没装 prometheus_client 自动降级 no-op，不影响启动）、重复注册不报错（模块级缓存兜住）、**低基数标签**（标签值不能是 question/file_path，否则 Prometheus 内存会爆）。

**延迟桶按用户感知档位选**（`common/metrics.py:103-107`）：0.1=无感，0.5=略慢，1/2/5=明显卡顿，10=不可接受。刻意不设 60s 桶 —— 超长尾的根因通常是下游挂了，会被单独的超时计数覆盖。

### 3.6 容器化交付

**非 root + uid 对齐**（`agent1.Dockerfile:56-65`）：

> ```
> # ★ uid/gid 必须与宿主用户一致，否则 compose 挂载目录一律Permission denied。
> #   这个坑的隐蔽之处在于：单独 docker run（不挂 output/）一切正常，
> #   镜像「验证通过」，一上 compose 就 PermissionError 崩溃。
> #   很容易误判成镜像有问题，实际是 uid 不匹配。
> ```

**必须整目录 COPY**（`:42-46`）：

> ```
> # ★ 这里必须整目录 COPY，不能用 COPY agent1/*.py agent1/。
> #   glob 只匹配当前层，agent1/eval/、agent1/ui/ 这些子目录会被整个漏掉 ——
> #   症状很隐蔽：镜像构建成功，但运行时一旦走到 eval/ui 的代码就报
> #   ModuleNotFoundError: No module named 'eval'。
> ```

**apt 包名写错的后果**（`:18-24`）：`libglib2.0-0` 在 python:3.10-slim（Debian 13）里已不存在，实际是 `libglib2.0-0t64`；某些包名会被 apt 当虚拟包静默解析，真正缺的是运行时库，症状要等到 import cv2 才暴露。

## 四、项目亮点（面试向）

> 这一节按「面试官会怎么问 → 你的答案要点」组织，每个亮点都能落到具体代码或数字上。
> **核心原则：数字必须能追问出下一层，且每层都能打开代码验证。**

### 亮点 1：我做的最关键的一件事，是先证明「问题在哪一层」

**面试官可能问**：这个项目你最大的挑战是什么？

**答题结构**：
1. **先给归因**：改造前 faithfulness=0.986 而 context_precision=0.165 —— faithfulness 高说明模型不编造，precision 低说明检索塞了噪声。这两个问题的解法完全不同，所以第一步是先归因。
2. **再给排查**：定位到检索层后，逐层拆出三个根因（精准路径无排序直接截断、精准命中短路跳过融合、dedup key 用 page_content[:80] 导致法条互相引用被误合并）。
3. **最后给证据**：faithfulness 全程稳在 0.98 不掉，说明改动全在检索层，没有靠改 prompt 掩盖。

**为什么这个答案有分量**：它证明的不是「我会调参」，而是「我知道什么时候不该动模型」。大多数人拿到 precision 低的第一反应是换更强的 LLM —— 而那恰恰是错的。

### 亮点 2：我能讲清一个「做了但回退」的优化

**面试官可能问**：讲一个你做过的最有技术含量的优化。

**答题结构**（**主动讲回退，比只讲成功更有说服力**）：
1. 动机：覆盖率用 bool 命中，10~32 个候选并列满分，把 BM25 的正确判断抹平了
2. 尝试：idf² 超线性加成，让「稀有词命中一次」压过「常见词命中多次」
3. 实测：直查法条 recall +0.050，但**跨文档综合 -0.143、陷阱题 -0.167**
4. 根因：跨文档答案分布在多份文件里，每个片段只命中 1 个词，单词命中在 idf² 下权重极高。**idf² 优化的是「找准那一条」，代价是「找齐那几条」**，而跨文档类占样本 45%
5. 决策：回退，但**保留 IDF 加权本身**，并把 BM25 与精排的 idf 上限拆成两个独立常量
6. 收获：「保留拆分的意义是今后调精排不会连带影响召回 —— 这是本轮最重要的结构性收获」

**关键句**：「错的是『超线性』这个选择，不是『加权』本身。」

### 亮点 3：我知道什么时候不该做优化

**面试官可能问**：你有没有做过效果不好的尝试？

**答题结构**：
1. 目录条目切分后答案块排名是 4/5/1，都进 top5 但很勉强，第 1 名是复述高频词的噪声
2. 我试了两种改覆盖率公式的方案，top2 稀有词确实更好（4→2）
3. **但只有 3 条样本，调参依据不足，泛化性未知，所以没有采用**
4. 决定等评测集更大时再动检索权重

**关键句**：「一个反向的能力展示：能做出 1 分提升的改动，但能判断出它不该现在做，比什么都重要。」

### 亮点 4：我的评测体系防的是「自己骗自己」

**面试官可能问**：你怎么保证优化有效，不是过拟合？

**答题结构**（这是最能拉开差距的一段）：
1. **空跑检测**：指纹只哈希 question + contexts，**绝不能含答案与分数** —— 含了分数一变指纹就变，空跑检测立刻失效。v7/v8/v9 三份报告指纹完全相同，就是空跑的铁证
2. **判据是「指纹一致 AND 分数有变」**，不是「指纹一致且超出噪声底」—— 指纹一致已意味着检索层零变化，此时任何分数变化都不可能是策略改进，只能是 LLM 抖动
3. **噪声底 0.10 而不是实测的 0.021**：因为单次 A/B 差值只是抖动幅度的**下界**；曾拿 0.021 当阈值设成 0.02，结果恰好卡在边界上测试直接失败
4. **不可比时不给 verdict** —— 比什么都不报更危险
5. **处置是阻断不是警告**：退出码 1 让脚本直接退出，因为错误结论一旦写进文档就会成为面试素材

**加分项**：可以主动提「弃答检测器换过 5 版才收敛，v2 误报 29 条、v4/v7 准确率来回震荡 0.81/0.85 —— 结论是**弃答是语义判断，不是字符串匹配**」。

### 亮点 5：我能把「机制存在」和「机制生效」分开

**面试官可能问**：你怎么保证那些治理机制真的起作用？

**答题结构**：
1. **熔断器案例**：`common/resilience.py` 里的 CircuitBreaker 三态实现完整漂亮，但 grep 全库只有它自己和它的单元测试引用 —— **业务代码零接入**
2. 为什么能长期存在：「只有单元测试覆盖 protected_call，无法发现『没人调用它』」。所以我测的是 `guarded_call` 这个**会被业务调用的入口**
3. **权限过滤案例**：过滤 expr 写得对，但当前语料 secret_level>2 的 chunk 数 = 0、valid_until 全为 0 —— 从未在真实数据上被验证过。我造了 5 密级 × 部门 × 有效期的 fixture + 可见性矩阵
4. **通用原则**：功能测试全过、单元测试全过，但直到某天接入真实涉密文档才发现过滤规则有漏洞 —— 那时候已经在生产环境，而且是在**越权访问**的场景下暴露的

**关键句**：「检查工具本身需要被检查。」

### 亮点 6：我理解执法场景和 demo 场景的差别在哪

**面试官可能问**：这个系统上线会遇到什么问题？

**答题结构**（**这一条最能体现你做过真实交付，不是跑过 demo**）：
1. **法规时效性**：「一份被废止的处罚规定如果还能被检索到并写进处罚决定书，那是会出执法事故的」—— 所以增量更新必须先删旧块再插新块，且**删除失败必须抛异常中断**，因为那是会出执法事故的静默失败
2. **降级方向**：「宁可给执法员一份没有 AI 解读的法条原文，也不要给一个编造的答案，也不要让整个请求失败」—— LLM 不可达时降级三级，最后一级保留已检索到的法条原文
3. **超时量级**：「执法场景等 10 分钟不可接受」—— 从 600s 收紧到 30s
4. **留痕可靠性**：审计是执法留痕的载体，「磁盘满、权限变更、目录被删 —— 任何一条触发，审计就静默丢失，而你**不会知道丢了**」。但默认不上抛，因为「审计服务故障拖垮执法业务」是更严重的事故
5. **权限分级**：dept / secret_level / valid_until 三重过滤，其中 valid_until 那条直接对应「已废止条款」的风险

### 亮点 7：我会主动评估方法论是否适用，而不是照搬

**面试官可能问**：你怎么看 Agent 的工具治理 / 记忆分层？

**答题结构**（**这条展示独立判断力，最容易让面试官记住你**）：
1. 我拿一份「Agent 工具调用治理」的方法论逐条对照了本项目，结论是 **8 个治理点里 6 个「不适用」或「已由别的机制覆盖」**
2. 理由很硬：本项目是**确定性编排**（LangGraph 固定流程 + 显式路由），**LLM 不选工具**，只在给定上下文里生成文本 —— 所以「模型会乱调用工具」这个前提在本项目根本不成立
3. 治理点不是「缺失」，而是「落点不同」：

| 方法论说的位置 | 本项目实际的位置 |
|---|---|
| 工具 Schema 校验 | 路由前的意图分类（三级级联）|
| 工具权限白名单 | JWT claims + 检索层过滤 |
| 调用频次限流 | `route_max_hops=3` |
| 结果后置校验 | 片段质量过滤 + 改动检测 |

4. 真正缺的只有一条（高危二次确认），而且后果严重
5. **而且我找到了一个方法论没提、更严重的隐患**：`thread_id` 秒级精度 —— 方法论讲「怎么隔离记忆」，但没讲「**隔离键本身会不会撞**」。同秒并发任务共享 checkpoint → 案情要素互相污染
6. 记忆分层机制本身**不需要引入**：项目是单任务型、无跨会话记忆需求，checkpointer 已按 thread_id 分区

**关键句**：「如果按那份方法论逐条实现，会给本项目加上一堆针对『LLM 乱选工具』的防护 —— 而本项目根本不让 LLM 选工具。那是**为了看起来完备而增加无用复杂度**。」

### 亮点 8：我的多智能体协作是「确定性编排」而非「LLM 自由决策」

**面试官可能问**：为什么用 LangGraph？多智能体怎么协作的？

**答题结构**：
1. **编排是固定的**：9 个节点、3 个条件边、LangGraph StateGraph。classify 按后缀分组 → 三个模态节点**并行** fan-out → synthesize 汇总 → extract_fields → doc_draft → review_submit → report
2. **LLM 的职责边界很清楚**：只在给定上下文里生成文本，不负责选工具、不负责决定流程走向
3. **这带来两个具体好处**：① 行为可预测 —— 每一步的输入输出都有契约（`docs/skills/` 里写了 5 份调用契约）；② 可回归 —— 状态图能重放，评测才能做
4. **State 设计有个细节**：`errors` 用 `Annotated[list[str], operator.add]`，多个节点并行报错能累加而不互相覆盖
5. **预算双检**：节点入口 + 条件边各查一次，超限降级到 report 并在 errors 里记明原因

### 亮点 9：我有「把结论钉在可验证的证据上」的纪律

**面试官可能问**：你项目里的数字怎么来的？

**答题结构**：
1. 每个数字都能打开文件核对：`report_rerank_final.json`（评测）、`agent1/build_index.py` 的 `_report_chunk_marks()`（索引标记）、`docs/case-stories.md` 的「数字速查」
2. **索引重建是否生效有唯一可信证据**（`agent1/build_index.py:423-436`）：「改动分块策略后评测分数常常纹丝不动，肉眼无法区分『策略无效』和『索引没重建』—— 只能直接查落库的标记」。所以重建后报告 is_catalog / is_tier_table 的实际数量
3. **我自己也犯过这个错**：写速查表时凭印象填了早期的 0.88 / 0.165，最新实测是 0.698 / 0.226
4. **工具化**：`deploy/tools/verify_story_numbers.py` 逐项核对 10 个数字的出处；`check_site.py` 三维自检（资源可达 / 锚点有效 / 结构完整）；`check_async_blocking.py` AST 门禁；`verify_skill_docs.py` 文档↔代码一致性校验（上线第一件事就抓出我自己写错的一处端点归属）

**关键句**：「面试时记错的数字比不记得更糟 —— 对方会顺着追问，你得能圆回来，而圆不圆得回去取决于你到底有没有真的做过。」

### 亮点 10（备用）：Docker 交付里那些「看起来是镜像问题、实际不是」的坑

**面试官可能问**：部署上遇到什么问题？

**答题结构**（挑一个讲就够）：
- **uid 不匹配**：单独 `docker run` 一切正常，一上 compose 就 PermissionError —— 很容易误判成镜像有问题，实际是挂载点属主与容器用户不一致
- **glob 漏子目录**：`COPY agent1/*.py agent1/` 会把 `agent1/eval/`、`agent1/ui/` 整个漏掉，症状是镜像构建成功、运行时才报 ModuleNotFoundError
- **apt 包名**：`libglib2.0-0` 在 Debian 13 已是 `libglib2.0-0t64`，写错的症状是构建 exit 100 或运行时才崩
- **探针分离**：`/health` 失败重启、`/ready` 失败摘流量，混成一个端点是最常见的误配 —— 依赖抖动导致服务被反复重启

## 五、已验证的缺陷与边界

> 这一节如实记录**本次核查中实测确认**的问题。写在这里是因为面试时可能被追问，
> 而「知道边界在哪」本身就是能力。

### 5.1 已修复：`logger` 未定义（5 个文件，35 处调用）

**根因**：`logger = logging.getLogger(...)` 在一次批量替换中被放进了**模块 docstring 内部**，它变成了文档文本而不是代码 —— 模块级没有 logger 定义。

**实测影响**（修复前）：

| 文件 | 调用数 | 触发路径 | 症状 |
|---|---|---|---|
| `agent1/server.py:482` | 1 | approve 检测到高风险且未确认 | **NameError → HTTP 500**（而非返回 `confirmation_required`）|
| `agent1/case_pipeline.py` | 24 | 文书生成主路径 | NameError → 被 `except Exception` 吞成 errors，**文书静默生成失败** |
| `agent1/case_field_matcher.py` | 2 | 抽取失败分支 | NameError |
| `agent1/field_resolver.py` | 1 | 处罚建议生成失败 | NameError |
| `common/tracing.py` | 7 | 异常处理分支 | NameError（仅异常路径触发）|

**修复**：把 `import logging` + `logger = logging.getLogger(...)` 移到模块级（docstring 之后；若文件有 `from __future__` 则必须在其之后 —— PEP 563 要求 `from __future__` 在模块 docstring 之后、任何其它语句之前）。

**验证**：

### 5.2 未接线：权限过滤未接入生产检索链路

**这是最需要如实说明的一条。**

**代码事实**：
- `agent1/retrieval_backend.py` 的 `_passes_filter` 实现了 dept / secret_level / valid_until 三重过滤，逻辑正确，且有 18 个测试覆盖
- 但生产 `/api/rag/ask` 的实际链路是 `rag_module.rag_ask` → `hybrid.get_hybrid` → **直连 FAISS，完全绕过 retrieval_backend**
- `agent1/server.py:232` 有一行直接的证据：`# TODO: phase5 透传 UserCtx 给检索层做权限过滤`
- `retrieval_backend.search` 的调用方只有 `agent1/eval/ragas_eval.py` 与 `agent1/demo/trace_pipeline.py`
- gateway 侧也不透传：`handle_rag(query, top_k)` 的请求体只有 `{"question", "top_k"}`，UserCtx 仅用于审计

**后果**：索引里 `dept` / `secret_level` / `valid_until` 三个字段在真实流量上**不参与过滤**。

**两处文档的归因有误**：

- `docs/agent-governance-review.md:64` 把「JWT claims + 检索层过滤」列为「工程兜底已经做在了别的位置」，与代码不符

2. `rag_module.rag_ask` 改走 `retrieval_backend.search`（或在 `hybrid` 上补过滤后处理）
