# RAG 调优路径 —— 5 轮迭代的完整推理

> 这份文档记录的不是"我调了什么参数"，而是**每一轮怎么发现问题、  
> 怎么排除错误假设、怎么验证结论**。
>
> 面试时这份文档的价值在于：它证明的不是结果，是**方法**。

---

## 起点：只有一个数字

```
faithfulness 0.986  answer_relevancy 0.880
context_precision 0.165  context_recall 0.600
```

`context_precision = 0.165` 很低。但**低在哪、为什么低、该改哪里，  
全都不知道**。这是 RAG 优化最常见的起点，也是最危险的起点 ——  
因为很容易直接去调权重、换模型、加 reranker，然后看着分数微动，  
误以为在优化。

---

## 第 0 步：先建尺子，再动手术

**问题**：5 条样本算出来的指标，置信区间宽到没有参考价值。  
用这种数据做决策，等于用体温计量血压。

**做法**：

1. **评测集扩到 47 条**，人工标注，三个维度设计：
   - `category`：直查法条 20 / 跨文档综合 21 / 陷阱题 6
   - `difficulty`：easy 8 / medium 18 / hard 21
   - 原始 7 条**完整保留**，保证与早期结果可比
2. **加分层统计**：按 category / difficulty 分组算指标
3. **加同口径归因**：老 7 条与新增 40 条分开统计

### 这里踩的第一个陷阱

新评测跑出来总分从 0.95 掉到 0.48。当时的第一反应是"代码退化了"。

**分层一看**：老 7 条 recall 仍是 1.000，新加的 40 条只有 0.444。  
总分是**新样本拉低**的，不是代码退化。

> **方法论**：扩充评测集后，总分变化必须先归因到"样本变化"还是  
> "代码变化"，否则会花大量时间调试一个根本没坏的系统。

### 分层立刻指出了方向

| category | n     | context_recall |
| -------- | ----- | -------------- |
| 直查法条     | 20    | 0.65           |
| 跨文档综合    | 21    | 0.44           |
| **陷阱题**  | **6** | **0.167**      |

陷阱题 recall 只有 1/6。逐条看，**4 条都与《消防产品目录》有关**。  
问题域瞬间收敛：从"整个 RAG 不好"变成"目录类文档检索失效"。

---

## 第 1 轮：P1 表格型分块

**假设**：裁量基准表（严重/一般/较轻并列）被切碎，语义中心分散，  
通用查询下容易"沾边即召回"。

**做法**：把"一个违法行为 + 它的全部档位"作为一个语义单元，  
写 `regroup_tier_table()`，加 `is_tier_table` 元数据，检索时降权 0.6。

**结果**：faithfulness 0.978 / relevancy 0.579 / precision 0.226 / recall 0.527。

---

## 第 2 轮：P2 目录降权 + **查询意图豁免**

**假设**：目录型 chunk（型号罗列、不含义务性表述）是噪声。

**做法**：`is_standard_catalog()` 判定并降权 1.2。

**结果**：**陷阱题 recall 从 0.167 降到 0.167（完全没变），  
但 faithfulness 从 0.978 升到 0.993。**

### 这里踩了第二个陷阱（重要）

我以为是"降权不够狠"，准备加大惩罚值。但逐条看才发现：  
**4/6 陷阱题 recall 为 0 的原因，是 P2 把用户需要的答案降权挤出了 top-k。**

用户问的恰恰是"消防产品目录涵盖哪些大类"，而这些 chunk 里就写着  
"一、电线电缆（3 种）"。我优化的是噪声，删掉的是答案。

**修复**：加**查询意图豁免** —— 用户明确在问目录本身时，目录 chunk 就是答案。

```python
_CATALOG_INTENT = re.compile(r"(目录|名录|清单|一览|哪些类|大类|认证程序)")

if query and _CATALOG_INTENT.search(query):
    return False
```

> **教训（我写在代码注释里的）**：  
> **降权判据只看 chunk 自身不够，必须叠一层查询意图。**  
> 同一个 chunk 对"电动自行车怎么处罚"是噪声，对"产品目录有哪些"是唯一答案。

这一条是整段调优里最重要的方法论收获。  
如果没有分层统计 + 逐条核对，很容易把"降权加大"当成正确方向一路调下去。

---

## 第 3 轮：P3 生成 prompt 强制来源标注

**问题**：某条样本 faithfulness 只有 0.75 —— 答案 904 字，把 4 个片段  
揉成一段叙述，夹了片段里没有的概括性表述。

**根因**：prompt 只说"只输出检索内容中真实出现的内容"，**没有要求可追溯**。  
模型把多个片段平均融合后，就分不清哪句话来自哪一段。

**做法**：加 4 条硬约束

1. 每条结论标 `[片段N]`
2. 禁止跨片段合并改写
3. 检索不足时明确说"检索内容不足"
4. 数字原文照抄

**结果**：faithfulness 0.990 / relevancy 0.630 / precision 0.217 / recall 0.505。

**但 recall 纹丝不动** —— 这本身就是个信号。见第 4 轮。

---

## 第 4 轮：分块策略变更 —— 索引根本没重建

分数连续两轮完全不变，我开始怀疑"是不是索引没重建"。

**验证**（这一步是关键的思维习惯）：

```python
# 直接查落库索引的元数据，而不是靠分数猜
_docs = list(index.docstore._dict.values())
n_cat = sum(1 for d in _docs if d.metadata.get("is_catalog"))
print(n_cat)   # -> 0
```

结果 `is_tier_table=79`（新版代码生效了）但 `is_catalog=0`。  
继续查，发现 P4 的判据从一开始就没命中过。

**根因**：`python build_index.py --force` 这个参数**根本不存在**  
（实际是 `--rebuild`），argparse 遇到未知参数直接退出。

**修复**：

1. 给 `--rebuild` 加 `--force` 别名
2. 在 `build_index.py` 启动时加**索引同步自检**
3. 重建完成后**直接报告落库的实际标记数**：
   ```
   分块标记：is_catalog=268  is_tier_table=9
   ```

> **教训**：**"效果完全不变"时，先确认代码是否真的执行，再分析策略。**  
> 这在生产环境里是高频事故 —— 半年后没人记得上次的重建命令是什么。

## 第 5 轮：P4 目录条目切分（三次判据修正）

**问题**：检索不到"电线电缆类产品包括哪些"的答案。  
逐层排查发现：**答案完整存在于一个 306 字 chunk 里，BM25 明确把它排第 1 名**，  
但被重排挤出 top-k。

分块后的 chunk 长这样：

```
一、电线电缆（3 种）1.不包括阻燃电线电缆、耐火电线电缆…  [前导：自我声明说明]
1.电线组件（0101） 适用于家用和类似一般设备所用的…        [后接：下一个条目]
```

答案被夹在两段无关内容中间，bag-of-words 无法对齐。

**根因**：PDF 的视觉结构在转纯文本后丢失了。

### 判据修正 1：为什么"中位间隔"是错的

最初的判据是"序号型切点的中位行间隔 ≤ 12 则认为是目录"。

实测该文档 35 个切点的间隔是 `[4, 269, 2, 349, 465, 218, 90, 42, ...]`，  
**中位数 95 行** —— 因为每个大类下面是一整张几十行的产品表。

> 任何"间隔要小"的阈值都会把它误判为非目录。  
> **这是"没有看真实数据就定阈值"的典型后果。**

改用切点总数判定（≥ 8）。

### 判据修正 2：为什么"行首匹配标准号"会误伤

第二份目录文档通篇没有任何序号，靠标准号锚定。但判据写成"行首匹配标准号"，  
结果《浙江省建筑工程消防验收操作技术导则》8561 行正文被切成 344 块。

因为导则正文里标准号是**句内引用**：

```
GB 50354 等技术标准检查验收合格基础上进行，施工记录…
```

行首一匹配就中招。

**修复**：要求标准号**独占整行**（正则尾部锚定 `$`）。

### 判据修正 3：优先级错了

改完还是 `is_catalog=0`。原因是 `_split_segment` 里  
`regroup_tier_table` 排在前面。目录公告每个条目都是  
"若干行说明 + 一个处罚档位"排版，整篇被判成档位表（45 块全标 tier_table），  
`is_catalog` 根本拿不到。

**修复**：把 P4 提到 P1 之前 —— 目录特征比档位特征更结构化、更难偶然命中。

### 全库 103 文件验证（判据零误伤）

| 文件          | 非空行  | 独占标准号行 | 占比        | 判定    |
| ----------- | ---- | ------ | --------- | ----- |
| 2020 认证目录公告 | 4056 | 365    | **9.00%** | ✅ 命中  |
| 2022 消防产品目录 | 2264 | 127    | **5.61%** | ✅ 命中  |
| 建筑工程消防验收导则  | 8561 | 13     | 0.15%     | ❌ 未误切 |
| 电动自行车建设导则   | 345  | 0      | 0.00%     | ❌ 未误切 |
| 其余 99 个文件   | —    | 0      | ~0        | ❌ 未误切 |

导则 0.15% vs 目录 5.61%，**差 37 倍**，阈值取 2% 留足安全边际。

**验证方法**：用 `pypdf` 抽**真实 PDF 全文**跑真实分块器，  
而不是拿旧索引的小 chunk 预演。

> 这个教训来得很直接：我最初用旧索引的 306 字 chunk 预演，  
> 而真实构建是整篇文档进函数，切点量级完全不同，  
> 导致判据连续改了三次都是错的。  
> **预演必须用真实输入粒度。**

### 验证是否真的落库

```bash
python build_index.py --rebuild
# 分块标记：is_catalog=268  is_tier_table=9
```

块数从 3819 → **4019**，与桌面端全量验证的结果逐份一致  
（2020 公告 153 块、2022 目录 116 块、导则 342 块）。

**注意 `is_tier_table` 从 79 降到 9 是正确的**：原先 79 里有 45 个是  
目录公告被误判成档位表，目录条目切分后不再走档位分支。

**结果**：陷阱题 recall **0.167 → 0.333**（翻倍）。

## 第 6 轮：真正的瓶颈在 prompt，不在检索

**现象**：`answer_relevancy` 长期停在 0.579，而 faithfulness 已达 0.99。  
检索看起来没问题，为什么生成侧这么低？

**交叉分析**（关键动作）：

| 分组           | 条数     | answer_relevancy 均值 |
| ------------ | ------ | ------------------- |
| 弃答（"检索内容不足"） | **34** | **0.429**           |
| 正常作答         | 13     | **0.969**           |

**34/47 条弃答**。RAGAS 的 answer_relevancy 判"答案是否切题"，  
说"答不出来"必然低分。

### 但弃答率高本身不是 bug

弃答在生产里是**正确行为**。分组后发现真正的问题是：

**14 条 recall ≥ 0.75 却仍然弃答** = 过度保守，答案就在片段里：

| 问题              | 片段里有什么                   | 模型为什么弃答            |
| --------------- | ------------------------ | ------------------ |
| 消防技术文书应当使用什么式样？ | ctx0 开头就是"消防行政法律文书式样"    | 直接弃答               |
| 消防法关于设施维护保养的要求？ | ctx3"应当每月进行维护保养，确保其完好有效" | 因"该片段未标明是《消防法》第几条" |
| 裁量基准是什么？        | 片段里有严重/一般/较轻档位           | 因"未完整、明确地写出整体性内容"  |

**共同的错误：把"完整"当成回答的前提。**  
而提问者要的往往是规则或定义，不是穷尽列举。

**修复**：prompt 第 3 条改为可操作判据 ——

> **只要有任意一个片段与问题相关，就必须基于它作答。**
>
> - 答案不完整、只覆盖部分情形，也要作答，末尾说明哪些情形未覆盖
> - 片段没有标明出处的，照样直接引用，不要因无法确认条款号而拒答
> - 只有**所有片段都与问题无关**时才说"检索内容不足"

**结果**：

| 指标               | v6    | v7        | 变化         |
| ---------------- | ----- | --------- | ---------- |
| answer_relevancy | 0.579 | **0.706** | **+0.127** |
| faithfulness     | 0.985 | 0.985     | **0.000**  |
| context_recall   | 0.527 | 0.548     | +0.021     |
| 弃答条数             | 34    | 11        | −23        |
| 过度保守             | 14    | 2         | −12        |

**"多作答不换来幻觉"** —— 少弃答 23 条，faithfulness 一条没掉。  
这推翻了我原本的假设，而**推翻假设本身是产出**。

## 附：一个检测器改 5 版的故事

第 6 轮里我想统计"有多少条弃答"，用来持续监控。  
最初只匹配字面 `"检索内容不足"`，结果漏掉换了措辞的弃答。

| 版本     | 做法             | v6        | v7        | 失败原因                             |
| ------ | -------------- | --------- | --------- | -------------------------------- |
| v1     | 只匹配一个短语        | 漏 20      | 漏 4       | 换个措辞就漏                           |
| v2     | 12 类否定模式组      | **误报 29** | **误报 29** | 新 prompt 让**正常答案**结尾也写"检索内容未覆盖…" |
| v3     | 加"必须无 [片段N]"   | 漏 9       | 漏 8       | 弃答答案里标注满天飞                       |
| v4     | 看 [片段N] 后 30 字 | 0.809     | 0.851     | 窗口怎么调都翻车                         |
| v5     | 只看开头 60 字      | 0.957     | 0.787     | 正常答案开头也有法定表述                     |
| **v6** | **LLM judge**  | —         | —         | —                                |

**最终结论**：**弃答是语义判断，不是字符串匹配。**  
同一个意思能被写成十几种说法，而正常答案里也随时出现否定词。  
词法规则在这件事上只会无限震荡。

改为复用项目已有的 LLM judge，与四个 RAGAS 指标同一套口径。  
词法版降级为无 API Key 时的兜底（实测漏判 0，可安全降级）。

**产出不是那个函数，而是"我知道什么时候该停止调参"。**  
v5 之后准确率还在 0.787~0.957 震荡，我就没再写第 6 版规则。

## 我拒绝做的一次优化

目录条目切分后，答案块排名是 4 / 5 / 1 —— 全部进 top5，但都很勉强。  
第 1 名是"3C 认证产品…认证证书编号"这类复述高频词的噪声。

我试了两种改覆盖率公式的方案：

| 方案       | 电线电缆    | 认证程序    | 涵盖大类 |
| -------- | ------- | ------- | ---- |
| 现状（纯覆盖率） | 4 ✅     | 5 ✅     | 1 ✅  |
| 基数惩罚     | 4 ✅     | **6 ❌** | 1 ✅  |
| top2 稀有词 | **2 ✅** | 5 ✅     | 1 ✅  |

top2 稀有词看起来更好（4→2），**但我没有采用** —— 只有 3 条样本，  
调参依据不足，泛化性未知。

我决定等评测集更大时再动检索权重。

> **一个反向的能力展示**：能做出 1 分提升的改动，  
> 但能判断出它不该现在做，比什么都重要。

## 完整指标演进

| 轮次        | faith     | relevancy | precision | recall    | 关键动作             |
| --------- | --------- | --------- | --------- | --------- | ---------------- |
| 初始（5 条）   | 0.986     | 0.880     | 0.165     | 0.600     | —                |
| v3（47 条）  | 0.978     | 0.579     | 0.226     | 0.527     | 扩评测集 + 分层统计      |
| v4        | 0.993     | 0.613     | 0.209     | 0.505     | P2 查询意图豁免        |
| v5        | 0.990     | 0.630     | 0.217     | 0.505     | P3 prompt        |
| v6（P4 落库） | 0.985     | 0.579     | 0.217     | 0.548     | 目录条目切分           |
| **v7**    | **0.985** | **0.706** | **0.221** | **0.548** | **prompt 修过度保守** |

**读这张表的方式**：

- v3 → v4 的 relevancy 下跌不是退化，是评测集口径变化
- v5 → v6 的 recall 上涨来自 P4，relevancy 下跌 0.63→0.579 是因为  
  弃答判定受检索结果变化影响
- v6 → v7 是**唯一一次四项指标全线上行且无代价**的改进

## 三条可迁移的方法论

1. **先建尺子，再动手术。** 没有分层统计和逐条核对，  
   我会把"加大降权"当成正确方向一路调下去。
2. **效果完全不变时，先确认代码是否真的执行。** 这个现象出现了两轮  
   （索引未重建、判据从未命中），成本都是半天。
3. **在 3 条样本上调出来的参数，不要用。** 提升是真实的，  
   但依据不足。知道"什么时候不做优化"和知道"怎么做"同样重要。

## 还没解决的

写在这里比被追问出来更好：

1. **context_recall 0.548**，主要卡在跨文档综合类（0.512）——  
   需要查询分解或多跳检索。
2. **陷阱题 precision 仅 0.100** —— 目录类问题的噪声过滤仍不够精细。
3. **评测集 47 条偏小**，置信区间宽。这是为什么我在 3 条样本上调出  
   的改进会主动放弃。
4. **LLM 故障转移尚未在真实故障下完整验证** —— 单元测试覆盖 24 种场景，  
   但需要 DeepSeek 恢复后重跑同模型评测，才能把"策略效果"与  
   "模型差异"分开。
